# PH-03 — Дошки, учасники та права

Статус: виконано 12.10.2026. Джерела: [вимоги](REQUIREMENTS.md#32-дошки), [матриця прав](REQUIREMENTS.md#2-ролі-та-права), [рішення PH-00](PH00_DECISIONS.md), [реалізація](IMPLEMENTATION.md#авторизація-ресурсів), [план фази](PHASES.md#6-ph-03--дошки-учасники-та-права).

## Реалізований результат

Avalonia показує свої дошки та дозволяє створити нову. Автор автоматично стає єдиним адміністратором. Адміністратор редагує назву й опис, додає вже зареєстрованого користувача за email, змінює дозволи на створення й видалення карток, відкликає доступ і видаляє дошку. Учасник читає дошку та список учасників; адміністративних кнопок у його інтерфейсі немає. Дозволи зберігаються й відображаються; застосування їх до CRUD карток належить PH-04.

Видалення й відкликання вимагають окремого підтвердження всередині застосунку. «Скасувати» не надсилає мутацію. За відсутності дощок є пояснення й форма створення; після входу список завантажується автоматично.

## Контракт API

Усі маршрути захищені JWT; префікс — `/api`.

| Метод | Маршрут | Результат і право |
| --- | --- | --- |
| GET | `/boards` | 200, лише свої дошки |
| POST | `/boards` | 201, дошка + адміністратор атомарно |
| GET | `/boards/{boardId}` | 200, учасник |
| PUT | `/boards/{boardId}` | 200, адміністратор |
| DELETE | `/boards/{boardId}` | 204, адміністратор |
| GET | `/boards/{boardId}/members` | 200, учасник |
| POST | `/boards/{boardId}/members` | 201, адміністратор |
| PATCH | `/boards/{boardId}/members/{userId}` | 200, адміністратор |
| DELETE | `/boards/{boardId}/members/{userId}` | 204, адміністратор |

Назва обов’язкова, до 150 символів; опис необов’язковий, до 4000. Значення обрізаються по краях. Email нормалізується так само, як при реєстрації. Новий учасник має роль `Member` і обидва дозволи `true`. Зміна ролей та передача адміністратора не входять до API.

`BoardDetailsDto.Version` — Base64 для 8 байтів SQL `rowversion`. Кожна мутація наявної дошки потребує актуальної версії: `ExpectedBoardVersion` у JSON для PUT/POST/PATCH; для обох DELETE — query `?expectedBoardVersion=<URL-encoded Base64>`. Створення дошки не потребує версії. Після мутації клієнт повторно читає деталі та учасників.

| Ситуація | HTTP / код |
| --- | --- |
| Відсутній або недійсний JWT | 401 / `unauthorized` |
| Учасник виконує адміністративну дію | 403 / `forbidden` |
| Ресурс відсутній або дошка недоступна | 404 / `not_found` |
| Email не належить зареєстрованому користувачеві | 404 / `user_not_found` |
| Дублювання учасника | 409 / `member_exists` |
| Зміна дозволів або видалення адміністратора | 409 / `admin_protected` |
| Застаріла версія | 409 / `concurrency_conflict` |
| Відсутня/некоректна версія або поля | 400 / `validation_failed` |

Перевірка членства перед перевіркою версії не дозволяє сторонньому користувачеві визначати стан чужої дошки через конфлікти. ID учасника перевіряється разом з ID дошки.

## Транзакції та права

`BoardAccess` читає поточне членство з БД, а не з JWT. Мутація виконується через стратегію повторення EF і явну транзакцію: перевірка права, умовне оновлення `Boards.RowVersion`, повторна перевірка права під блокуванням, предметна зміна, збереження та commit. Дві зміни з однаковою версією дають одного переможця й один 409. Невдала операція відкочує також версію дошки.

Відкликання прибирає `AssigneeId` лише з карток цієї дошки, оновлює їх часову мітку та версію, зберігає `CreatedById`, коментарі й користувача. Видалення дошки явно прибирає зв’язки тегів, зображення, коментарі, картки, колонки, теги й членство в одній транзакції. Користувачі та інші дошки зберігаються. Для цих сценаріїв немає нової міграції: використано схему PH-01.

Призначення відповідального й решта мутацій карток у PH-04 мають використовувати цей самий шлюз, щоб вони були узгоджені з відкликанням доступу. Підхід до транзакцій відповідає документації Microsoft про [транзакції EF Core](https://learn.microsoft.com/en-us/ef/core/saving/transactions) та [ExecuteUpdate/ExecuteDelete](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete).

За 409 клієнт отримує нову версію без автоматичного повторення запису й зберігає незбережені назву та опис. За 404 недоступна дошка й учасники прибираються з кешу, список оновлюється. Вихід скасовує активний запит та очищає форми/кеш; запізніла відповідь не відновлює приватні дані. Періодичне оновлення ще належить PH-05; зараз сервер застосовує відкликання до наступного запиту, UI реагує при «Оновити» або наступній дії.

## Фактична перевірка

- Повний набір: **49 пройшли, 0 помилок, 0 пропусків**, з них 30 на справжньому MSSQL 2022 через емуляцію `linux/amd64` на цьому Mac.
- 13 нових серверних SQL-тестів: CRUD, усі захищені маршрути, сторонній користувач, учасник, дублювання, адміністратор, валідація, відкликання, одночасні зміни, ізоляція дошки та повне видалення.
- Окремі SQL-тести штучно викликають помилку наприкінці видалення дошки/учасника й підтверджують відкат уже видалених дочірніх даних, призначень і версій.
- 5 нових клієнтських тестів: наскрізний сценарій через API/MSSQL, вихід під час запиту, збереження чернетки за конфлікту, безпечна помилка повторного читання, підтвердження/скасування.
- **27 нативних HTTP-перевірок** через окремий процес API. Найдовший запит у цій пробі — 996 мс; це одинична проба, перевірка навантаження 20 користувачів залишається PH-08.
- Живий Avalonia: створення/перейменування, додавання учасника, збереження дозволів, підтвердження та скасування видалення, вхід учасника без адміністративних елементів, реакція на відкликання, вихід і збережений список після повторного входу адміністратора. Фактичне видалення перевірено HTTP та наскрізним тестом ViewModel.
- Release: **0 попереджень, 0 помилок**. EF підтвердив відсутність змін моделі після міграції. Тимчасову HTTP/GUI-БД прибрано; її відсутність окремо перевірено запитом до MSSQL.

[Машинний протокол](PH03_RESULTS.json) містить результати TRX, HTTP та GUI. [Скриншоти](screenshots/ph03/README.md) знято з реального застосунку з вигаданими тестовими обліковими записами.

## Відтворення

За підготовленого `.env`, повного SDK і готового SQL:

```sh
scripts/dotnet.sh build Curs.sln -c Release
python3 scripts/verify-ph01.py ph03
scripts/dotnet.sh ef migrations has-pending-model-changes --project KanbanApi --no-build
scripts/dotnet.sh build Curs.sln
python3 scripts/verify-ph03-http.py
```

Для GUI додати `--gui` до останнього скрипта й запустити клієнт з `KANBAN_API_URL=http://127.0.0.1:5043/`. Скрипт створює лише тимчасові дані; після перевірки закрити клієнт і перервати скрипт для очищення. Повсякденний запуск описано в [README](../README.md#підготовка-локального-середовища).

## Наступна фаза

PH-04 додає колонки, картки, теги та коментарі, включно з фактичними заборонами створення/видалення карток. Drag-and-drop та автоматичне оновлення — PH-05; фото — PH-06; контейнер API — PH-07; остаточне навантаження — PH-08.

## Уточнення для Rider після завершення фази

12.10.2026 виправлено показану користувачем помилку аналізу `InitializeComponent` у `BoardWorkspaceView`: конструктор явно викликає [AvaloniaXamlLoader.Load(this)](https://docs.avaloniaui.net/api/avalonia/markup/xaml/avaloniaxamlloader). `partial` збережено, бо Avalonia генерує другу частину класу під час компіляції; лише хибне попередження Rider `PartialTypeWithSinglePart` має локальний `SuppressMessage` з поясненням. Помилки компілятора й інші перевірки не вимкнено. Коміт — [6822341](https://github.com/kuum-oss/Curs/commit/6822341).

Після виправлення Release усього рішення пройшов із 0 помилок і 0 попереджень; повторно пройшли 27 нативних HTTP-перевірок. У живій Release-збірці перевірено вхід, завантаження `BoardWorkspaceView`, створення дошки та відкриття її деталей з реального MSSQL. Показані у скриншоті користувача діагностики файла в Rider усунено. Тимчасову БД перевірки прибрано. Початковий протокол PH-03 вище збережено як історичний результат фази.
