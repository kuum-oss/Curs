# План реалізації KanbanBoard

Версія документа: 1.10. Оновлено: 19.10.2026. Статус: PH-00–PH-08 виконано; результати підтверджені тестами, навантаженням і живим Avalonia.

Основа — [вимоги](REQUIREMENTS.md) та [рішення PH-00](PH00_DECISIONS.md). Структура, маршрути, поля та алгоритми є робочим планом, а не завершеними функціями. Користувач визначив запуск на одному Mac, пробу MSSQL через емуляцію та нативний клієнт; решту базових правил деталізовано рішеннями поточної фази.

## 1. Архітектура

```text
Avalonia-клієнт (нативний процес macOS)
    Views → ViewModels → API services → HttpClient + JWT
                                      |
                                      v
ASP.NET Core Web API (Docker)
    Controllers → Application services → EF Core
                                      |
                                      v
Microsoft SQL Server 2022 (Docker, persistent volume)
```

Клієнт не підключається до БД напряму. Валідація в UI допомагає користувачеві, а остаточні перевірки даних, прав і зв'язків виконує сервер. API не передає EF-сутності клієнту: використовуються окремі DTO.

### Запланована структура рішення

```text
Curs.sln
Curs/                          # існуючий Avalonia-клієнт
  Views/
  ViewModels/
  Services/                    # API, сесія, навігація, зображення
  Models/                      # стан UI, обгортки DTO
  Assets/
KanbanApi/
  Controllers/
  Application/                 # сценарії, авторизація ресурсів
  Domain/                      # сутності, enum, правила
  Infrastructure/              # DbContext, EF-конфігурації, JWT, BCrypt
  Contracts/                   # HTTP-запити та відповіді
  Migrations/
  Dockerfile
KanbanContracts/               # спільні DTO та enum без залежності від EF
KanbanApi.Tests/
docs/
compose.yaml
.env.example
```

Сервер залишається одним проєктом із логічним поділом на шари. Окремі бібліотеки для кожного шару не потрібні для базового обсягу курсової. `KanbanApi/Contracts` містить суто серверні контракти, спільні з клієнтом контракти розміщуються в `KanbanContracts` без дублювання.

У PH-01 створено всі чотири проєкти рішення з `net10.0`, зафіксовано SDK 10.0.103 та EF Core/SQL Server provider 10.0.12. Avalonia залишається 11.3.12. Реалізовано сутності, міграцію, основу HTTP/MVVM та обробку помилок; предметні маршрути й екрани зі структури вище додаються в наступних фазах. Фактичні результати й інструкції — у [PH01_IMPLEMENTATION](PH01_IMPLEMENTATION.md).

## 2. Модель даних

Ідентифікатори сутностей — `uniqueidentifier` (`Guid`). Дата дедлайну — SQL `date` / C# `DateOnly?`; часові мітки — UTC у `datetime2`. Текст — Unicode `nvarchar`. Нижче наведені запропоновані ліміти, яких немає у вихідному ТЗ.

| Таблиця | Основні поля |
| --- | --- |
| Users | `Id`, `Email nvarchar(254)`, `NormalizedEmail nvarchar(254)`, `Name nvarchar(100)`, `PasswordHash varchar(100)`, `SessionVersion int`, `RowVersion rowversion`, `AvatarData varbinary(max) NULL`, `CreatedAtUtc` |
| Boards | `OwnerId NULL`, `IsArchived bit`, `CoverOriginalData varbinary(max) NULL`, `CoverThumbnailData varbinary(max) NULL`, `CoverContentType NULL`, `Id`, `Name nvarchar(150)`, `Description nvarchar(4000) NULL`, `CreatedAtUtc`, `UpdatedAtUtc`, `RowVersion rowversion` |
| BoardMembers | `BoardId`, `UserId`, `Role`, `CanCreateCards bit`, `CanDeleteCards bit`, `JoinedAtUtc`, `IsFavorite bit`, `LastOpenedAtUtc NULL` |
| Columns | `Id`, `BoardId`, `Name nvarchar(100)`, `Position int`, `RowVersion rowversion` |
| Cards | `IsArchived bit`, `Id`, `ColumnId`, `Title nvarchar(200)`, `Description nvarchar(max) NULL`, `DueDate date NULL`, `Priority tinyint`, `AssigneeId NULL`, `Position int`, `CreatedById`, `CreatedAtUtc`, `UpdatedAtUtc`, `RowVersion rowversion` |
| Tags | `Id`, `BoardId`, `Name nvarchar(50)`, `NormalizedName nvarchar(50)`, `Color varchar(7)` |
| CardTags | `CardId`, `TagId` |
| CardImages | `Id`, `CardId`, `ContentType varchar(50)`, `OriginalName nvarchar(255)`, `SizeBytes int`, `OriginalData varbinary(max)`, `ThumbnailData varbinary(max)`, `ThumbnailContentType varchar(50)`, `CreatedAtUtc` |
| Comments | `Id`, `CardId`, `AuthorId`, `Text nvarchar(4000)`, `CreatedAtUtc`, `EditedAtUtc NULL`, `RowVersion rowversion` |

Опис картки має ліміт 10 000 UTF-16 одиниць; у PH-01 його захищено CHECK-обмеженням `DATALENGTH <= 20000`, прикладна валідація додається з CRUD. Кольори тегів — `#RRGGBB`. Порожні назви й коментарі мають відхилятися предметними маршрутами. `Role`: `Admin = 0`, `Member = 1`; `Priority`: `Low = 0`, `Medium = 1`, `High = 2`, `Critical = 3`.

### Зв'язки

- `Users ↔ Boards` — багато-до-багатьох через `BoardMembers`.
- `Boards → Columns → Cards` — один-до-багатьох.
- `Boards → Tags`; `Cards ↔ Tags` — через `CardTags`.
- `Cards → CardImages` — нуль або одна обкладинка, забезпечено унікальністю `CardId`.
- `Cards → Comments`; `Comments.AuthorId → Users.Id`.
- `Cards.AssigneeId → Users.Id` — необов'язковий зв'язок; належність до дошки перевіряється окремо.
- `Cards.CreatedById → Users.Id` — автор створення; це не відповідальний.

Дошка картки визначається через її колонку, тому дубль `BoardId` у `Cards` не потрібен. API перевіряє, що колонки переміщення, теги та відповідальний належать одній дошці. Перевірка членства й зміна картки виконуються в транзакції, узгодженій з відкликанням членства, щоб паралельні операції не залишили невалідне призначення.

### Ключі, індекси та цілісність

- Унікальний індекс `Users.NormalizedEmail`.
- Складені первинні ключі `BoardMembers(BoardId, UserId)` і `CardTags(CardId, TagId)`.
- У PH-08 індекс одного адміністратора знято другою міграцією. `Boards.OwnerId` визначає захищеного початкового власника; сервіс ролей не дозволяє зняти його адміністрування або лишити дошку без адміністратора.
- Індекси `BoardMembers(UserId, BoardId)`, `Columns(BoardId, Position)`, `Cards(ColumnId, Position)`, `Cards(AssigneeId)`, `Cards(DueDate)`, `Cards(Priority)`.
- Унікальність `Tags(BoardId, NormalizedName)` та `CardImages(CardId)`.
- Індекс `Comments(CardId, CreatedAtUtc, Id)` для стабільного порядку.
- CHECK-обмеження на enum, невід'ємні позиції та допустимий розмір оригіналу зображення.

Індекси позицій не робляться унікальними: під час перенумерації можливі тимчасові збіги. Відсутність дублів у фінальному порядку забезпечується транзакційним алгоритмом і тестами. Пошук за входженням підрядка перевіряється на реальному наборі даних; звичайний індекс назви не гарантує прискорення такого пошуку.

Для зв'язків використовується явне `NoAction` там, де каскади SQL Server створювали б кілька шляхів видалення. Залежні дані дошки або колонки видаляє сервіс у транзакції: спочатку `CardTags`, `CardImages`, `Comments`, потім `Cards`, `Columns`, `Tags`, `BoardMembers` і `Boards`. Для окремої колонки видаляється лише її піддерево, теги дошки залишаються. Видалення користувачів у базовому API не передбачене.

## 3. Серверна логіка й безпека

### Автентифікація

1. Реєстрація перевіряє дані, нормалізує email та створює BCrypt-хеш із сіллю бібліотеки.
2. Реалізований ліміт пароля: від 8 UTF-16 одиниць, не більше 72 байтів UTF-8, щоб не допустити непомітного обрізання BCrypt. Work factor — 12; окремі нативні HTTP-вимірювання наведено в результатах PH-02, навантаження перевіряється у PH-08.
3. Вхід звіряє хеш та повертає JWT, його строк дії і дані користувача. Неправильний email або пароль дають однакову відповідь.
4. JWT містить `sub = UserId`, `jti`, `iat`, `exp`, `sv = SessionVersion`, issuer та audience; строк дії — рівно 24 години. API перевіряє підпис, issuer, audience, строк дії та актуальний `SessionVersion` користувача; допустиме часове відхилення задається явно.
5. Секрет підпису передається через конфігурацію середовища; для HMAC-SHA256 — випадковий ключ щонайменше 32 байти.
6. JWT зберігається лише в пам'яті клієнта. Після закриття застосунку потрібен новий вхід. Логи не містять паролів і токенів.

У PH-02 ці сценарії реалізовано через `/api/auth/register`, `/api/auth/login` та `/api/auth/me`, BCrypt.Net-Next 4.2.0 і JwtBearer 10.0.12. `ClockSkew = 0`, алгоритм — HS256. Вхід, реєстрація й вихід працюють у Avalonia. [Результати й перевірки PH-02](PH02_AUTHENTICATION.md).

### Авторизація ресурсів

Права дошки не записуються в JWT: сервер читає актуальне членство й дозволи з БД. Так відкликання доступу діє для наступних запитів без очікування завершення JWT. Кожен endpoint перевіряє ланцюг ресурсу до дошки, включно з читанням зображень.

Немає токена або він недійсний — `401`; учаснику бракує права на відому дошку — `403`; ресурс відсутній або дошка недоступна користувачеві — `404`. За `401` клієнт очищає сесію та відкриває вхід.

У PH-03 реалізовано `BoardAccess` і `BoardService`: читання дощок, адміністративні зміни, учасники та дозволи. Зміна починається з умовного оновлення `Boards.RowVersion` у транзакції; після отримання блокування повторно перевіряються права. У PH-04 цей механізм застосовано також до колонок, карток, тегів і коментарів, включно з призначенням відповідального. [Фактична реалізація і перевірки PH-03](PH03_BOARDS.md).

### Одночасна робота та порядок

- Клієнт отримує Base64-представлення `RowVersion` у DTO та передає його для зміни відповідного ресурсу.
- Зміни структури дошки, порядку карток, членства і дозволів додатково перевіряють та оновлюють `Boards.RowVersion` як версію спільного стану.
- Перевірка версії дошки, зміни ресурсів і запис нового порядку — одна транзакція. Сервіс спочатку умовно оновлює дошку за очікуваною версією, а потім виконує операцію; блокування утримується до завершення транзакції.
- Це правило поширюється на всі мутації дошки, включно з коментарями й обкладинками, щоб механізм оновлення клієнтів бачив кожну зміну.
- Порядок колонок і карток зберігається як `Position = 0..N-1`. Нова картка додається в кінець.
- Для переміщення картки передаються цільова колонка та `BeforeCardId` або `null` для кінця. Сервер перевіряє опорну картку, вилучає переміщувану зі старого списку, вставляє в новий та перенумеровує обидва списки атомарно.
- Для колонок клієнт передає повний список їхніх ID: кожен ID належить дошці й зустрічається рівно один раз.
- Невідповідність версії дає `409 Conflict`. Клієнт оновлює дані й повідомляє про конфлікт; автоматичного перезапису чужої зміни немає.

У PH-05 реалізовано `OrderingService`, атомарну повну перестановку колонок та перенесення карток. Клієнт змінює порядок до HTTP-відповіді й відновлює його за помилки. За 409 він отримує поточні версії та зберігає незбережені поля. [Фактичні перевірки PH-05](PH05_COLLABORATION.md).

У PH-05 працює перевірка версії відкритої дошки кожні 5 секунд та завантаження змін. За незмінної версії виконується лише GET метаданих; відкликання доступу очищає приватний вміст навіть із відкритим редактором. Дозволений лише один активний запит оновлення; якщо він не завершився, наступний цикл пропускається. При відкритому редакторі незбережені поля не перезаписуються; під час перетягування оновлення відкладається до його завершення. SignalR можна додати пізніше, якщо потрібне миттєве оновлення; це не початкова вимога.

## 4. Контракт API

У PH-03–PH-06 працюють маршрути автентифікації, дощок, учасників, колонок, карток, тегів і коментарів у таблиці нижче. Порядок/переміщення реалізовано у PH-05, фільтри й фото — у PH-06. Для `PUT` дошки, `POST` учасника та `PATCH` дозволів поле `ExpectedBoardVersion` обов’язкове в JSON. Обидва `DELETE` передають його в query: `?expectedBoardVersion=<URL-encoded Base64>`. Це 8 байтів SQL `rowversion`, а не довільний текст. Створення дошки не потребує версії.

Префікс: `/api`. Формат метаданих: JSON. Захищені запити: `Authorization: Bearer <JWT>`. Створення повертає `201`, читання й оновлення — `200`, видалення — `204`. Версії змінених ресурсів після `204` клієнт отримує повторним читанням.

| GET | `/boards` | Мої дошки |

| DELETE | `/boards/{boardId}/members/{userId}` | Відкликання доступу |

Окремий серверний endpoint виходу не потрібен для погодженого варіанта з очищенням клієнтської сесії. Створення тегу входить до заповнення поля «теги»; перейменування й видалення тегів як окремі функції не входять до базового ТЗ.

У PH-04 `ExpectedBoardVersion` обов’язкове для кожної мутації вмісту; `ExpectedVersion` також потрібне для перейменування/видалення колонки, редагування/видалення картки й додавання коментаря. Обидва поля DELETE — у query. Сторінка карток читається в RepeatableRead через стратегію EF; клієнт звіряє версію між усіма сторінками й повторним читанням метаданих. [Результати PH-04](PH04_CONTENT.md).

PH-05: `PUT columns/order` приймає `ColumnIds` і `ExpectedBoardVersion`; `POST cards/{cardId}/move` — `TargetColumnId`, `BeforeCardId` (null для кінця), `ExpectedBoardVersion` та `ExpectedVersion` картки. Обидва повертають 200 з новою версією дошки; move також повертає нову версію картки. Чужа колонка — 404, некоректна опора/перестановка — 400, застаріла версія — 409.

### Параметри та DTO

- Список карток: `search`, `priority`, `tagId`, `assigneeId`, `due=overdue|today|upcoming`, `today=YYYY-MM-DD`, `offset`, `limit`. `today` обов'язковий при активному `due`; неправильні параметри дають `400`.
- Пагінація: типове `limit = 100`, максимум 500; порядок `Column.Position`, `Card.Position`, `Card.Id`. Клієнт догружає сторінки й дозволяє перестановку карток лише після завантаження повного нефільтрованого списку. Неповна дошка має видимий стан завантаження.
- Усі сторінки списку містять `BoardVersion`; клієнт приймає їх лише з однаковою версією, інакше перечитує список. Перед drag-and-drop сервер однаково перевіряє поточну версію.
- Коментарі завантажуються сторінками зі стабільним порядком за датою та ID; відповідь містить загальну кількість.
- `CardSummaryDto`: ID, колонка, позиція, назва, дедлайн, пріоритет, відповідальний, теги, `HasImage`, версія. Бінарні зображення й повні описи в список не включаються.
- `CardDetailsDto` додатково містить опис і метадані обкладинки; коментарі отримуються окремо.
- Запити зміни мають `ExpectedBoardVersion` та, коли змінюється існуюча картка/колонка, її `ExpectedVersion`. Для DELETE версії передаються у явно документованих query-параметрах; для multipart — окремими полями форми.
- `MoveCardRequest`: `TargetColumnId`, `BeforeCardId`, `ExpectedVersion`, `ExpectedBoardVersion`.

Помилки повертаються як `ProblemDetails` зі стабільним кодом і, для валідації, помилками полів. Типові статуси: `400` — дані некоректні, `401` — немає авторизації, `403` — бракує права, `404` — ресурс недоступний, `409` — конфлікт, `413` — завеликий файл, `415` — непідтримуваний формат. Внутрішній текст винятків та SQL не передається клієнту.

PH-06 реалізує `CardQuery`: search, priority, tagId, assigneeId, deadline і today. Фільтри поєднані AND, регістр назви не враховується, `%`/`_` є буквальними символами. Пагінація фільтрується до підрахунку кількості й зберігає початкові позиції. Клієнт завантажує всі сторінки з однаковими умовами, скасовує старий пошук і оновлює календарну вибірку після локальної півночі.

Розширені маршрути профілю, аватарів, обкладинок дощок, ролей, архіву та коментарів наведено в [контракті PH-08](PH08_DESKTOP.md#api-розширення). Друга міграція `SketchParityProfiles` оновлює наявні дані без очищення БД. Приклади запитів і схема — [матеріали захисту](PH08_DEFENSE.md).

## 5. Зображення

1. API приймає один файл до 5 МіБ. Загальний ліміт multipart-запиту трохи більший через службові поля, але ліміт саме файлу залишається 5 МіБ.
2. Сервер перевіряє розмір, сигнатуру та можливість повного декодування JPG, PNG або WEBP. Розширення не є доказом формату.
3. У PH-06 застосовано межі до 20 мегапікселів і до 10 000 пікселів по стороні. Сервер використовує Magick.NET-Q8-AnyCPU 15.0.0; пакет і ліцензії перевірені. Дозволено лише декодери JPEG/PNG/WEBP; паралельне декодування обмежено двома операціями.
4. Оригінал зберігається у `OriginalData`, превью зі стороною до 480 пікселів — у `ThumbnailData`; для кожного зберігається його фактичний MIME-тип.
5. Заміна обкладинки та оновлення версій виконуються атомарно; невдала обробка не прибирає попередню обкладинку.
6. Відповіді зображень — бінарні з правильним `Content-Type`. `HttpClient` додає JWT; не можна покладатися на публічну URL-адресу для захищених фото.
7. Клієнт кешує байти превью за сесією, ID та версією картки: до 8 МіБ/128 записів, до чотирьох завантажень. Фото догружаються для видимих карток; кеш і bitmap очищаються при виході/втраті доступу. Пізня відповідь старої сесії не повертає фото.

Реалізовано атомарні PUT/DELETE та захищені GET оригіналу/PNG-превью. PUT приймає один multipart File і обидві версії; DELETE — версії у query. Відповіді фото мають фактичний MIME, no-store/private і nosniff. Нова картка спочатку зберігається, потім отримує фото. [Результати PH-06](PH06_FILTERS_IMAGES.md).

### Поведінка

- Усі мережеві операції асинхронні з можливістю скасування; очікування не блокує UI-потік.
- Списки оновлюються через прив'язані колекції; для великої дошки використовуються віртуалізація або завантаження видимого вмісту.
- Є стани завантаження, порожніх даних, помилки та повторного запиту. Подвійне натискання «Зберегти» не створює дубль.
- Кнопки відображають поточні права; обмеження після оновлення дошки застосовуються відразу.
- У PH-05 drag-and-drop через захват указателя Avalonia відрізняє колонку від картки та прив’язаний до поточного вікна/дошки. Поріг — 6 пікселів, індикатор — синя межа, прокручування — крок 14 пікселів кожні 40 мс; Escape або втрата захвату скасовують жест. Кнопки редактора не є джерелами перенесення.
- На завершення перетягування порядок відразу оновлюється в UI, потім надсилається один запит. За помилки клієнт перечитує підтверджений стан або повертає попередній, якщо API недоступний.
- Пошук має затримку близько 300 мс після введення; попередній запит скасовується, а застаріла відповідь не підміняє новішу.
- Закриття редактора з незбереженими змінами потребує підтвердження.

## 7. Docker та запуск

У PH-07 реалізовано [Dockerfile API](../KanbanApi/Dockerfile), [Compose](../compose.yaml) та [.dockerignore](../.dockerignore). Авторитетна конфігурація — ці файли; покрокова інструкція — [DEPLOYMENT](DEPLOYMENT.md), фактичні результати — [PH-07](PH07_DOCKER.md).

- Контекст збірки — корінь рішення через залежність KanbanContracts; allowlist передає лише сервер, контракти та global.json, без bin/obj або секретів.
- SDK 10.0.103 та ASP.NET runtime 10.0.13 зафіксовані digest. Публікація — linux-$TARGETARCH без self-contained runtime, запуск — непривілейований користувач на 8080. Restore/publish/видалення кешу пакетів — у тому самому шарі для малого Docker-диска.
- Перевірений digest MSSQL 2022 із PH-00 збережено, платформа SQL — linux/amd64. API на поточному Mac — linux/arm64. Це перевірка емуляції для курсової, а не офіційна підтримка SQL на ARM.
- Compose чекає SQL healthcheck SELECT 1, потім API перевіряє JWT і застосовує EF-міграції до відкриття HTTP. Помилка дає керований код виходу 1; EnsureCreated не використовується.
- Readiness перевіряє доступність БД і міграції, liveness — HTTP-процес. Healthcheck образу виконує dotnet KanbanApi.dll --healthcheck на localhost:8080. Втрата БД дає 503; відновлення потребує свіжої успішної проби, попередній Docker healthy не гарантує готовність відразу після старту SQL.
- Для обох сервісів restart unless-stopped. Статус unhealthy сам по собі не є причиною автоматичного restart.
- MSSQL_SA_PASSWORD і JWT_KEY надходять з виключеного з Git .env; .env.example містить лише placeholders. API_PORT, SQL_PORT і KANBAN_DATABASE необов’язкові. Стандартні порти 5000 і 3038 прив’язані до 127.0.0.1; LAN не входить до погодженого обсягу.

Запуск: `docker compose up --build -d --wait --wait-timeout 240`. Клієнт працює нативно з `KANBAN_API_URL=http://127.0.0.1:5000/`, у Rider або через scripts/dotnet.sh run --project Curs.

Іменований sqlserver-data зберігає всі дев’ять таблиць, включно з оригіналами й превью фото; окремий volume API не потрібен. Restart і штатний down без -v зберігають volume. Down -v видаляє дані; volume не замінює резервної копії. Скрипт verify-ph07-docker.py перевіряє свіжу БД, усі три формати Linux, restart/down/up і втрату SQL в окремому випадковому проєкті та прибирає тільки власний тимчасовий volume.

## 9. Перевірка реалізації

- **Модульні перевірки:** матриця дозволів, граничні дати дедлайнів, валідація та вставлення картки на початку, всередині й у кінці.
- **Інтеграційні перевірки на MSSQL 2022:** міграції, унікальність email, усі зв'язки, транзакційні видалення, відкликання доступу, `rowversion`, паралельні переміщення та призначення відповідального. EF InMemory не підтверджує поведінку SQL Server.
- **API-перевірки:** чужі ID, недійсний JWT, усі заборонені дії, невалідні параметри, надмірний розмір і хибний формат зображення.
- **Наскрізна перевірка:** два незалежні клієнти на одній дошці, зміни полів, порядок, коментарі, фото, відкликання доступу та мережевий збій.
- **Навантаження:** 20 авторизованих користувачів на погодженому наборі даних; час запитів, помилки й узгодженість порядку після завершення.
- **Збереження:** повторний запуск контейнерів і клієнта, перевірка всіх даних та обкладинок.
- **UI:** фактичний запуск Avalonia, превью, повне зображення, фільтри, плавність перетягування й правильне відновлення після помилки.

Для звіту курсової зберегти схему БД, приклади API, скриншоти основних екранів, результати перевірок та опис запуску. Успішна збірка не замінює перевірку GUI, MSSQL, Docker чи багатокористувацького сценарію.
