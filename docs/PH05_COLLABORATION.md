## Реалізований результат

Колонки переставляються за заголовок; картки — за тіло, між колонками та всередині колонки. Верхня/нижня половина картки означає вставлення до/після неї, вільне місце колонки — додавання в кінець. Ліва/права половина колонки означає вставлення до/після неї; окрема зона під дошкою ставить колонку в кінець. Порожня колонка також приймає картку.

Жест обробляється через захоплення вказівника Avalonia всередині поточного вікна. Поріг початку — 6 логічних пікселів; звичайне натискання не змінює порядок, кнопки редактора не запускають перенесення. Місце вставлення підсвічується синьою межею. Біля краю прокручуваної області виконується крок 14 пікселів і продовження кожні 40 мс. Escape, втрата захоплення й закриття представлення скасовують жест. Перенесення між різними вікнами не виконується.

Порядок у прив’язаних колекціях змінюється до очікування HTTP-відповіді. На сервер надсилається одна мутація. За помилки відновлюється попередній порядок; за 409 додатково завантажується актуальний стан. Незавершені операції після виходу не повертають приватний кеш. Перетягування дозволено після повного узгодженого завантаження дошки та закриття редактора. Для PH-06 підготовлено заборону перестановки карток у фільтрованому списку.

Відкрите представлення перевіряє метадані дошки кожні 5 секунд. Незмінна версія потребує лише одного GET та не перебудовує рядки. Одночасно виконується лише одне оновлення; цикл пропускається під час перенесення або власної мутації. Повільне фонове читання не блокує введення у поля редактора.

Коли інший користувач змінює дошку, відкритий редактор зберігає поля, вибрані теги й початкові версії; показується повідомлення про зовнішні зміни. Дозволи оновлюються відразу. Збереження старої версії відхиляється, чернетка залишається, автоматичного повторного запису немає. Після 409 клієнт отримує поточні версії; повторне збереження є окремою дією користувача. Відкликання доступу очищає картки, редактор, теги й коментарі навіть з чинним JWT.

## API та атомарність

| Метод і маршрут після `/api` | JSON | Результат |
| --- | --- | --- |
| PUT `/boards/{boardId}/columns/order` | `ColumnIds`: повна перестановка ID; `ExpectedBoardVersion` | 200, нова `BoardVersion` |
| POST `/cards/{cardId}/move` | `TargetColumnId`, `BeforeCardId` або null, `ExpectedBoardVersion`, `ExpectedVersion` картки | 200, ID/колонка, версія картки й дошки |

Потрібні JWT та актуальне членство. Заборони створення/видалення карток не забороняють їх переміщення або перестановку колонок. Чужий ресурс чи цільова колонка іншої дошки — 404; некоректна/власна опорна картка та неповна/повторна перестановка — 400; застаріла версія — 409.

`OrderingService` використовує транзакційний шлюз `BoardAccess`: умовне оновлення версії дошки, блокування, повторна перевірка членства, зміна та commit. Позиції обох колонок картки стають `0..N-1`; для перестановки колонок перевіряються всі ID рівно один раз. Опис, дедлайн, пріоритет, теги, відповідальний, історія коментарів і фото не змінюються. Фото перевірено SQL-фікстурою; завантаження й показ фото в UI належать PH-06. Нової міграції не потрібно.

Вимірювання відгуку отримано з `Stopwatch` у реальних обробниках за `KANBAN_VERIFY_DRAG=1`; це час обробника й локальної зміни колекцій, а не час повного рендеру екрана або мережі. Під час жестів UI реагував, HTTP очікується асинхронно. Нативний HTTP-прогін містив одну холодну реєстрацію 2145 мс; загальну вимогу 2 секунд та навантаження 20 користувачів перевіряємо у PH-08, успіх для всіх операцій зараз не заявляється.

Повний відкат перевірено штучними SQL-тригерами, що дають помилку після початку оновлення: позиції, версії ресурсів та дошки повертаються до початкових. За двох одночасних переміщень із тією самою версією успішне лише одне; друге отримує 409. Окремо у цьому SQL-сценарії одночасні редагування й переміщення тієї самої картки також мають одного переможця, без часткового змішування результатів. Недоступну мережу моделює транспорт, що кидає `HttpRequestException` після видимого оптимістичного перенесення.

Повний AC-05, AC-07, AC-12 та AC-14 підтверджено в межах PH-05; NFR-07 перевірено локальними жестами й асинхронним очікуванням. NFR-01, загальна NFR-02 та контейнерний API ще потребують наступних фаз.

## Відтворення

За готового SQL і локального `.env`:

```sh
scripts/dotnet.sh build Curs.sln -c Release
python3 scripts/verify-ph01.py ph05
scripts/dotnet.sh ef migrations has-pending-model-changes --project KanbanApi --no-build
scripts/dotnet.sh build KanbanApi
python3 scripts/verify-ph05-http.py
```

Для двох нативних клієнтів залишити API командою `python3 scripts/verify-ph05-http.py --gui`; використати `KANBAN_API_URL=http://127.0.0.1:5045/`. Скрипт створює лише тимчасову БД з випадковим іменем; після GUI закрити клієнти й перервати скрипт для очищення. Тестові паролі/JWT та локальний `.env` у звіт не включені.

Порядок публікації: усі перевірки → push `ph-05` і перевірка remote HEAD → fast-forward `main`, push та перевірка remote HEAD. Тематичні коміти наведено в [журналі фаз](PHASES.md#запис-виконання-ph-05). Наступна фаза — PH-06: пошук, фільтри та фото.
