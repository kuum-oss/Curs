# PH-08 — особистий чат між учасниками

Доповнення за прямим запитом користувача від 17.10.2026: кнопка «Чат» на картках сторінки «Команда» та особисте листування. [Вимоги](REQUIREMENTS.md), [протокол](PH08_PRIVATE_CHAT_RESULTS.json).

## Використання

«Команда» → «Чат» біля іншого учасника → ввести текст → «Надіслати». Власна картка не має кнопки чату. У лівій панелі «Чати» відкриває всі наявні розмови. Нова розмова можлива з користувачем спільної дошки; вже створена особиста переписка зберігається й після припинення спільної роботи на дошці.

Доступні історія з датою/часом, різні бульбашки своїх і вхідних повідомлень, попередній перегляд останнього тексту та лічильники непрочитаного. Історія завантажується по 50 повідомлень; «Попередні повідомлення» додає старіші. Відкритий розділ опитується кожні 2 секунди без перекриття запитів. Текст — до 2000 символів, Enter додає рядок, відправлення — окремою кнопкою. Порожні повідомлення не надсилаються. Вкладення, групові чати, редагування й видалення повідомлень у цей запит не входили.

Чернетки не губляться при переходах між розмовами/сторінками. При збої відправлення текст зберігається, повторна спроба має той самий ідентифікатор і не дублює повідомлення. Після успіху поле очищується. Вихід стирає листування й чернетки з пам’яті клієнта; пізня відповідь не може додати їх у новий сеанс. Закриття клієнта не видаляє серверну історію.

## Ізоляція та збереження

API перевіряє двох учасників для кожної операції. Інший користувач отримує 404 при читанні, відправленні та позначенні прочитаного; анонімний — 401. Членство на дошці чи роль адміністратора не дає доступу до чужого діалогу. Відповіді мають `no-store`.

На пару користувачів існує один діалог; одночасне відкриття з обох боків не створює дві розмови. Відправлення серіалізоване блокуванням рядка діалогу, унікальний `(ChatId, ClientMessageId)` захищає повторні запити. Курсор ID забезпечує порядок і сторінки без дублікатів; клієнт відстежує отриманий курсор окремо від власної відправки, тому не пропускає вхідний текст перед власною відповіддю. Позначка прочитаного тільки зростає й приймає ID повідомлення саме цього діалогу.

Під час семи днів запланованого видалення збережена історія лишається, надсилання такому користувачу вимкнене. При вході до строку доступ відновлюється разом з аккаунтом. Після остаточного очищення посилання на видаленого учасника й автора стають null; другий учасник бачить «Видалений користувач» та старі тексти без можливості надсилання. Коли видалені обидва учасники, діалог і його повідомлення очищуються. Захист чотирьох demo-аккаунтів не змінено.

## API та міграція

| Метод і шлях | Дія |
| --- | --- |
| `GET /api/chats` | Власні діалоги, останні повідомлення, непрочитані |
| `POST /api/chats` | Відкрити/створити діалог за `recipientId` |
| `GET /api/chats/{id}/messages` | Останні 50; `beforeId` для історії або `afterId` для нових |
| `POST /api/chats/{id}/messages` | Текст та незмінний `clientMessageId` повторної спроби |
| `POST /api/chats/{id}/read` | Монотонний `lastReadMessageId` |

П’ята міграція `20261017115129_PrivateChats` додає `DirectChats` і `DirectMessages`: поточна модель має **11 доменних таблиць**, початкові дев’ять збережені. Усі FK мають `NoAction`; очищення явне й транзакційне. Downgrade не дозволяє непомітно видалити повідомлення (SQL 50003). Модель відповідає міграціям. Дані зберігаються у тому самому MSSQL volume.

## Перевірки

**148 тестів із реальною MSSQL: 0 помилок, 0 пропусків.** Шість серверних/міграційних перевірок охоплюють ізоляцію, паралельне відкриття/відправлення, повтори, валідацію, сторінки, читання, очищення після семи днів та захист downgrade. Чотири клієнтські перевірки — повтори без дублів, вхідне повідомлення перед власним, чернетки та вихід під час запиту. Після остаточної косметичної зміни відображення помилки повторно пройшли всі 4 клієнтські тести. Release — без помилок і попереджень.

Production Docker API: **20 HTTP-запитів** перевірили обмін в обидві сторони, один діалог на пару, повторне відправлення, непрочитані та заборону сторонньому. Скрипт `scripts/verify-chat-http.py` створив три випадкові власні тестові аккаунти й дошку; прибрав лише ці точні ID з перевіркою префікса email та відсутності demo-захисту. Міграції застосовані в робочому Docker; API й SQL healthy, volume збережено.

Нативна перевірка CUA: на «Команда» є кнопки біля інших учасників; кнопка Олени відкриває діалог. Перевірочний текст надіслано з Avalonia, прочитано API від імені другого вигаданого demo-учасника; відповідь з API автоматично з’явилась у вікні. Після закриття, повторного запуску й входу обидва повідомлення завантажилися зі збереженої історії; остаточний скриншот оглянуто. Існуючі demo-акаунти не видалялися, їхні профілі та дошки не редагувалися. Два перевірочні повідомлення залишені в діалозі як приклад роботи. API-перевірка використовувала окремі випадкові записи. Паролі/JWT не входять до звіту.
