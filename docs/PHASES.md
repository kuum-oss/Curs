# Фази виконання курсового проєкту KanbanBoard

Версія: 1.0. Дата: 11.10.2026. Статус: план виконання та відстеження результатів.

Документ деталізує етапи 0–8 з [плану реалізації, розділ 8](IMPLEMENTATION.md#8-етапи-реалізації). Для кожної фази визначено передумови, роботи, очікуваний результат, перевірку та документи, на які вона спирається. Терміни й виконавці поки не призначені.

## 1. Документи та їх призначення

| Документ | Для чого використовується у фазах |
| --- | --- |
| [README](../README.md) | Призначення проєкту, технології, структура документації та опис поточного стану |
| [REQUIREMENTS](REQUIREMENTS.md) | Що система має робити: функції `FR`, обмеження `NFR`, права та критерії приймання `AC` |
| [IMPLEMENTATION](IMPLEMENTATION.md) | Як реалізувати вимоги: архітектура, таблиці, API, алгоритми, клієнт і Docker |
| [Ескізи інтерфейсу](sketches/README.md) | Візуальні орієнтири для головної дошки, деталей картки, списку дощок і керування учасниками |
| [Рішення PH-00](PH00_DECISIONS.md) | Вибір користувача щодо запуску та робочі правила предметної області |
| [Перевірка середовища PH-00](PH00_ENVIRONMENT.md) | Фактична доступність Docker/.NET та SQL-проба емуляції |
| **PHASES — цей документ** | У якій послідовності виконувати роботи та якими результатами підтверджувати завершення |

Вимоги визначають функціональний обсяг. План реалізації містить технічні пропозиції. Ескізи визначають напрям дизайну, але не додають нові функції: обкладинки дощок та зміна ролей, які з'явилися на згенерованих зображеннях, не є автоматично погодженими вимогами.

При зміні рішення спочатку узгодити й оновити відповідний документ-джерело, потім цей план. Якщо ескіз суперечить погодженим правам або обмеженням, реалізація має відповідати вимогам.

## 2. Поточний стан та порядок роботи

На 11.10.2026 підготовлено вимоги, план реалізації та чотири ескізи. PH-00 виконано: користувач визначив запуск, робочі правила записано, Compose-конфігурацію та MSSQL на ARM перевірено запитами й перезапуском. У коді залишається стартовий Avalonia-клієнт; API та міграцій ще немає. Наступна фаза — PH-01.

| Фаза | Назва | Передумови | Поточний статус |
| --- | --- | --- | --- |
| PH-00 | Уточнення вимог і середовища | Початкове ТЗ та наявні документи | Виконано 11.10.2026; рішення та SQL-проба підтверджені |
| PH-01 | Основа рішення та база даних | PH-00 | У роботі |
| PH-02 | Автентифікація та сесія | PH-01 | Заплановано |
| PH-03 | Дошки, учасники та права | PH-02 | Заплановано |
| PH-04 | Колонки, картки, теги та коментарі | PH-03 | Заплановано |
| PH-05 | Drag-and-drop та спільна робота | PH-04 | Заплановано |
| PH-06 | Пошук, фільтри та фото | PH-04; для повної інтеграції PH-05 | Заплановано |
| PH-07 | Docker та збереження даних | PH-01 для початку; PH-02–PH-06 для завершення | Заплановано |
| PH-08 | Приймання та матеріали захисту | PH-00–PH-07 | Заплановано |

Основний порядок: `PH-00 → PH-01 → PH-02 → PH-03 → PH-04 → PH-05 → PH-06 → PH-07 → PH-08`.

MSSQL потрібен уже в PH-01: на ранніх фазах база може працювати в контейнері, а API запускатися з Rider. PH-07 завершує контейнеризацію всієї серверної частини. Механізми версій і транзакцій проєктуються в PH-01 та застосовуються в PH-03–PH-04; PH-05 інтегрує їх із переміщеннями та багатокористувацьким UI.

## 3. PH-00 — Уточнення вимог і середовища

**Мета:** зафіксувати правила, які впливають на архітектуру та перевірку проєкту.

**Посилання на документи:**

- [REQUIREMENTS, розділ 2 — ролі та права](REQUIREMENTS.md#2-ролі-та-права): права учасників і адміністратора.
- [REQUIREMENTS, розділ 3 — функціональні вимоги](REQUIREMENTS.md#3-функціональні-вимоги): запропоновані правила полів, дедлайнів, видалення та зображень.
- [REQUIREMENTS, розділ 5 — відкриті уточнення](REQUIREMENTS.md#5-обмеження-та-відкриті-уточнення): Docker, macOS та цільове середовище.
- [IMPLEMENTATION, розділ 7 — Docker та запуск](IMPLEMENTATION.md#7-docker-та-запуск): варіант розгортання і доступ із локальної мережі.
- [Ескізи інтерфейсу](sketches/README.md): напрям дизайну та застереження щодо згенерованих елементів.

**Роботи:**

- [x] Перевірити архітектуру цільової машини — ARM64; користувач обрав пробу MSSQL через емуляцію.
- [x] Підтвердити доступність MSSQL 2022 фактичними запитами та повторним запуском.
- [x] Узгодити нативний запуск Avalonia та запуск API і БД через Compose.
- [x] Визначити підключення — один комп'ютер; користувач обрав моделювання 20 сесій у тесті.
- [x] Зафіксувати робочу матрицю прав, видалення непорожньої колонки та відкликання доступу.
- [x] Зафіксувати семантику дедлайнів, ліміти полів, одну обкладинку та правила фільтрації.
- [x] Визначити робочий спосіб оновлення дошки й тестовий набір для 20 користувачів.

**Результат:** узгоджені рішення записано у REQUIREMENTS та IMPLEMENTATION; ескізи використовуються в межах погодженого обсягу.

Поточні рішення й результат виконання зібрано у [PH00_DECISIONS](PH00_DECISIONS.md) та [PH00_ENVIRONMENT](PH00_ENVIRONMENT.md). Окремі відповіді користувача відрізняються від технічних робочих правил, обраних у межах цієї фази.

**Завершення:** відкриті питання, що блокують наступну фазу, вирішено; для відкладених питань визначено фазу, до початку якої потрібне рішення. Наявність документів сама по собі не означає погодження.

## 4. PH-01 — Основа рішення та база даних

**Мета:** підготувати структуру для розробки та створити реальну схему MSSQL.

**Передумова:** завершено PH-00 у частині архітектури, середовища та моделі даних.

**Посилання на документи:**

- [README — технології](../README.md#технології): обов'язковий стек.
- [IMPLEMENTATION, розділ 1 — архітектура](IMPLEMENTATION.md#1-архітектура): проєкти, шари та залежності.
- [IMPLEMENTATION, розділ 2 — модель даних](IMPLEMENTATION.md#2-модель-даних): дев'ять таблиць, зв'язки, індекси та правила видалення.
- [IMPLEMENTATION, розділ 3 — серверна логіка](IMPLEMENTATION.md#3-серверна-логіка-й-безпека): версії, транзакції та авторизація ресурсів.
- [IMPLEMENTATION, розділ 4 — контракт API](IMPLEMENTATION.md#4-контракт-api): DTO, маршрути та формат помилок.

**Роботи:**

- [ ] Додати `KanbanApi`, спільні контракти та проєкт серверних тестів до рішення.
- [ ] Налаштувати конфігурацію, ін'єкцію залежностей і єдину обробку помилок.
- [ ] Створити сутності та EF-конфігурації для всіх дев'яти таблиць.
- [ ] Реалізувати ключі, індекси, `rowversion` і безпечні правила зв'язків.
- [ ] Підготувати початкову міграцію та застосувати її до MSSQL 2022.
- [ ] Підготувати базові клієнтські сервіси API, сесії та навігації.

**Результат:** проєкти збираються; існує перевірена схема БД та основа API/MVVM. Предметні функції ще не вважаються готовими.

**Завершення:** міграція успішно створює БД із запланованими таблицями й обмеженнями; повторний запуск не створює дублікати. Фактичне підключення до MSSQL перевірено, а не підмінено EF InMemory.

## 5. PH-02 — Автентифікація та сесія

**Мета:** забезпечити реєстрацію, вхід, JWT-авторизацію та вихід.

**Передумова:** PH-01.

**Посилання на документи:**

- [REQUIREMENTS, розділ 3.1 — автентифікація](REQUIREMENTS.md#31-автентифікація): `FR-AUTH-01`–`FR-AUTH-04`.
- [REQUIREMENTS, розділ 4 — нефункціональні вимоги](REQUIREMENTS.md#4-нефункціональні-вимоги): `NFR-03`, `NFR-04`.
- [IMPLEMENTATION — автентифікація](IMPLEMENTATION.md#автентифікація): BCrypt, JWT, секрети й зберігання сесії.
- [IMPLEMENTATION, розділ 4 — API](IMPLEMENTATION.md#4-контракт-api): `/auth/register`, `/auth/login`, `/auth/me`.
- [IMPLEMENTATION, розділ 6 — клієнт](IMPLEMENTATION.md#6-avalonia-клієнт): екрани входу та реєстрації.

**Роботи:**

- [ ] Реалізувати реєстрацію з перевіркою email, пароля й імені.
- [ ] Зберігати BCrypt-хеш; перевірити обробку повторного email.
- [ ] Реалізувати вхід, видачу JWT на 24 години та перевірку токена.
- [ ] Створити Avalonia-екрани входу й реєстрації та перехід до списку дощок.
- [ ] Додавати JWT до захищених запитів; обробляти `401`.
- [ ] Реалізувати вихід з очищенням токена, даних сесії та кешу.

**Результат:** користувач може створити обліковий запис і розпочати або завершити сесію.

**Завершення:** виконано `AC-01`; перевірено неправильний пароль, повторний email, недійсний і прострочений JWT. Вихід очищає клієнтську сесію відповідно до погодженого правила, а не заявляється як серверне відкликання токена.

- [IMPLEMENTATION — авторизація ресурсів](IMPLEMENTATION.md#авторизація-ресурсів): актуальне членство й перевірка доступу на сервері.
- [IMPLEMENTATION, розділи 2 і 4](IMPLEMENTATION.md#2-модель-даних): `Boards`, `BoardMembers`; [маршрути API](IMPLEMENTATION.md#4-контракт-api).

**Роботи:**

- [ ] Реалізувати список своїх дощок, створення, редагування та видалення дошки.
- [ ] Автоматично створювати адміністративне членство автора дошки.

- [ ] Реалізувати відкликання доступу, захист адміністратора та очищення призначень відповідального в межах дошки.

**Результат:** дошки та учасники керуються через UI й API; сторонній користувач не читає чужу дошку.

**Завершення:** виконано `AC-02`, `AC-03` та адміністративну частину `AC-04`; перевірено `NFR-08` для наявних ресурсів. Повна перевірка заборон створення/видалення карток і непорожніх колонок завершується у PH-04.

## 13. Облік виконання

За інструкцією користувача від 11.10.2026 кожна завершена логічна зміна фіксується окремим тематичним комітом після перевірки. Після завершення фази її статус і докази оновлюються та комітяться; усі коміти фази відправляються на GitHub. Віддалений HEAD перевіряється перед повідомленням про успішну публікацію. Правила для наступних робіт збережено у [AGENTS.md](../AGENTS.md).

Допустимі статуси: **Заплановано**, **У роботі**, **Потребує рішення**, **На перевірці**, **Виконано**. Статус «Виконано» ставиться після перевірки результату, а не лише після написання коду.

Для кожної завершеної фази додати запис за формою нижче.
