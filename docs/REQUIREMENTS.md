# Вимоги до системи KanbanBoard

Версія документа: 1.3. Оновлено: 19.10.2026. Статус: базове ТЗ, рішення PH-00 та пряме розширення користувача для PH-08.

Джерело — технічне завдання замовника. Позначення `FR` — функціональні вимоги, `NFR` — нефункціональні, `AC` — критерії приймання. Уточнення та їх походження зафіксовано у [рішеннях PH-00](PH00_DECISIONS.md): D-01–D-03 — вибір користувача, решта — робочі правила реалізації. Вони не означають, що функції вже виконані.

## 1. Призначення та межі

KanbanBoard забезпечує багатокористувацьке планування завдань на спільних дошках. Дошка містить впорядковані колонки, колонки — впорядковані картки. Картки мають опис, дедлайн, пріоритет, теги, відповідального, обкладинку та коментарі.

До обсягу робіт входять Avalonia-клієнт, ASP.NET Core API, MSSQL, міграції EF Core, локальна Docker-інфраструктура та перевірка основних сценаріїв.

Веб-інтерфейс і хмарне розгортання виключені вимогами ТЗ. Відновлення пароля, email-підтвердження, refresh-токени, сповіщення, вкладення довільних форматів та офлайн-синхронізація не задані й не входять до базового плану.

## 2. Ролі та права

- **Гість:** реєстрація та вхід.
- **Учасник дошки:** робота з дошкою в межах наданих прав.
- **Адміністратор дошки:** керування учасниками й обмеженнями, видалення дошки. Автор нової дошки отримує цю роль.

Ролі належать конкретній дошці. Адміністратор однієї дошки не отримує доступ до інших дощок.

### Робоча матриця доступу

ТЗ явно визначає адміністративні права на видалення дошки, відкликання доступу й обмеження створення/видалення карток. Решту прав деталізовано робочими рішеннями D-04–D-08 так:

| Дія | Адміністратор | Учасник |
| --- | --- | --- |
| Перегляд дошки, учасників, карток та зображень | Так | Так |
| Редагування назви й опису дошки | Так | Ні |
| Видалення дошки | Так | Ні |
| Надання та відкликання доступу | Так | Ні |
| Зміна прав учасника | Так | Ні |
| Створення, перейменування, видалення й переміщення колонок | Так | Так |
| Створення карток | Так | Якщо `CanCreateCards = true` |
| Видалення карток | Так | Якщо `CanDeleteCards = true` |
| Редагування й переміщення карток | Так | Так |
| Зміна тегів, відповідального та обкладинки | Так | Так |
| Додавання коментарів | Так | Так |
| Фільтрація та пошук | Так | Так |

Правило PH-08: адміністратор може змінювати ролі учасників; початковий власник лишається захищеним адміністратором. Дошка не може лишитися без адміністратора. Новий учасник отримує обидва дозволи на картки; обмеження застосовуються до ролі учасника. Адміністратор не може відкликати власний доступ.

Видалення непорожньої колонки вважається також видаленням її карток: учасник із `CanDeleteCards = false` не може виконати таку дію. Видалення порожньої колонки дозволене. Сервер перевіряє права незалежно від стану кнопок клієнта.

## 3. Функціональні вимоги

### 3.1. Автентифікація

| ID | Вимога |
| --- | --- |
| FR-AUTH-01 | Реєстрація за email, паролем та ім'ям |
| FR-AUTH-02 | Вхід за email і паролем |
| FR-AUTH-03 | Авторизація захищених запитів за JWT |
| FR-AUTH-04 | Вихід із системи та повернення до екрана входу |

Робочі уточнення: email унікальний без урахування регістру; пароль не обрізається й не нормалізується. При виході клієнт видаляє JWT і очищає дані поточної сесії. При звичайному виході виданий токен залишається чинним до завершення строку дії. У PH-08 зміна пароля збільшує версію сесії на сервері та негайно робить усі попередні JWT користувача нечинними.

### 3.2. Дошки

| ID | Вимога |
| --- | --- |
| FR-BOARD-01 | Створення дошки; автор автоматично стає адміністратором |
| FR-BOARD-02 | Перегляд списку дощок, до яких користувач має доступ |
| FR-BOARD-03 | Редагування назви та опису дошки |
| FR-BOARD-04 | Видалення дошки лише адміністратором |
| FR-BOARD-05 | Надання доступу іншому користувачеві за email |
| FR-BOARD-06 | Відкликання доступу лише адміністратором |
| FR-BOARD-07 | Окреме обмеження права учасника створювати та видаляти картки |

Робочі уточнення: доступ надається вже зареєстрованому користувачеві; листи-запрошення не надсилаються. Повторне додавання не створює дубль членства. Відкликання доступу прибирає користувача зі списку можливих відповідальних і знімає його призначення з карток цієї дошки. Його попередні коментарі зберігаються.

### 3.3. Колонки

| ID | Вимога |
| --- | --- |
| FR-COLUMN-01 | Створення колонки на дошці |
| FR-COLUMN-02 | Перейменування колонки |
| FR-COLUMN-03 | Видалення колонки |
| FR-COLUMN-04 | Зміна порядку колонок за допомогою drag-and-drop |

Робочі уточнення: нова колонка додається в кінець; назва обов'язкова. Видалення непорожньої колонки потребує підтвердження в інтерфейсі й видаляє її картки разом із залежними даними. Переміщення колонки до іншої дошки не передбачене.

### 3.4. Картки

| ID | Вимога |
| --- | --- |
| FR-CARD-01 | Створення картки з назвою, описом, дедлайном, пріоритетом, тегами, відповідальним та фото-обкладинкою |
| FR-CARD-02 | Редагування будь-якого поля картки |
| FR-CARD-03 | Переміщення картки між колонками однієї дошки через drag-and-drop |
| FR-CARD-04 | Сортування карток усередині колонки через drag-and-drop |
| FR-CARD-05 | Видалення картки з перевіркою прав |
| FR-CARD-06 | Додавання та перегляд коментарів: текст, автор, дата |

Пріоритети: `Low`, `Medium`, `High`, `Critical`. Відповідальний обирається лише серед поточних учасників тієї самої дошки.

Робочі уточнення: обов'язковими є назва та пріоритет; типовий пріоритет — `Medium`. Опис, дедлайн, теги, відповідальний і обкладинка можуть бути відсутні. Дедлайн — календарна дата без часу. Переміщення між різними дошками не входить до базового обсягу. Коментарі відображаються від найстарішого до найновішого; у PH-08 автор може редагувати власний коментар, автор або адміністратор — видаляти його. Редагування має версію й дату зміни.

### 3.5. Фільтрація та пошук

| ID | Вимога |
| --- | --- |
| FR-FILTER-01 | Фільтр за пріоритетом |
| FR-FILTER-02 | Фільтр за тегом |
| FR-FILTER-03 | Фільтр за відповідальним |
| FR-FILTER-04 | Фільтр за дедлайном: прострочені, сьогодні, upcoming |
| FR-FILTER-05 | Пошук карток за назвою |

Робочі правила: активні фільтри поєднуються через логічне `AND`; пошук — входження підрядка без урахування регістру. Прострочені картки мають дату раніше сьогодні, «сьогодні» — рівну поточній даті, upcoming — пізніше сьогодні. Картки без дедлайну не входять до цих трьох вибірок. Сьогодні визначається за локальною датою клієнта, яку він передає в API.

Фільтрація не змінює збережений порядок. Робоче правило інтерфейсу: переміщення карток тимчасово недоступне за активного пошуку або фільтрів, оскільки приховані картки роблять позицію вставлення неоднозначною. Переміщення колонок залишається доступним.

## 4. Нефункціональні вимоги

| ID | Вимога | Як перевіряти |
| --- | --- | --- |
| NFR-01 | Одночасна робота до 20 користувачів | Навантажувальний сценарій із 20 авторизованими користувачами та перевіркою цілісності даних |
| NFR-02 | Стандартні API-операції виконуються не довше 2 секунд | Вимірювання читання, створення, редагування, видалення та переміщення на погодженому наборі даних |
| NFR-03 | Паролі зберігаються як BCrypt-хеші | Перевірка записів БД і процесу входу; відкритих паролів у БД та логах немає |
| NFR-04 | Строк дії JWT — 24 години | Перевірка різниці `exp` і часу видачі та відмови після закінчення строку |
| NFR-05 | API та БД запускаються через Docker Compose однією командою; Avalonia-клієнт працює нативно за рішенням користувача D-03 | Запуск серверної частини та успішний запит готовності API; окремий запуск клієнта |
| NFR-06 | Дані зберігаються у Docker volume при перезапуску контейнерів | Створення даних, перезапуск і повторне читання тих самих даних |
| NFR-07 | Drag-and-drop працює без затримок | Візуальна перевірка плавності; мережевий запит не блокує UI |
| NFR-08 | Авторизація дотримується при кожному доступі до ресурсів | Прямі запити з ідентифікаторами чужої дошки, картки, коментаря та зображення |

Робоча база вимірювань: 10 дощок, 10 колонок і 500 карток на кожній; 20 активних користувачів на одному комп'ютері. Детальний сценарій — [рішення PH-00, розділ 5](PH00_DECISIONS.md#5-план-перевірки-продуктивності). Для кожної стандартної операції фіксуються максимум, p95 та кількість помилок. Критерій ТЗ — до 2 секунд, тому сам по собі прийнятний p95 не компенсує перевищення в інших стандартних запитах. Завантаження фото й холодний запуск вимірюються окремо. Параметри машини та тривалість тесту потрібно записати у звіті.

Робоча ціль для UI: візуальний відгук на перетягування до 100 мс на тестовій машині. Після невдалої операції клієнт відновлює підтверджений сервером стан і показує помилку.

## 5. Обмеження та відкриті уточнення

1. Десктопний клієнт — лише Avalonia UI; веб-інтерфейс не створюється.
2. БД — Microsoft SQL Server 2022; альтернативна СУБД не підставляється без зміни ТЗ.
3. Розробка — Rider на macOS; розгортання — локальне.
4. Користувач погодив запуск API та БД через Compose і нативний Avalonia-клієнт (D-03). Базова версія працює на одному комп'ютері; доступ із LAN не потрібен (D-02).
5. Перевірено ARM64 на поточному Mac. Користувач обрав практичну пробу MSSQL через емуляцію (D-01); її результат фіксується у [перевірці середовища](PH00_ENVIRONMENT.md). SQL Server-контейнери підтримуються Microsoft на Linux x86-64; емуляція на Apple Silicon не є підтримуваною конфігурацією. [Офіційна документація Microsoft](https://learn.microsoft.com/en-us/sql/linux/containers/deploy?view=sql-server-ver16).
6. Матриця прав, видалення, дедлайни, ліміти та оновлення спільної дошки визначені як [робочі рішення PH-00](PH00_DECISIONS.md). Patch-версії нових пакетів та бібліотека обробки зображень перевіряються до початку їх використання у PH-01 та PH-06 відповідно.

## 6. Критерії приймання

| ID | Сценарій | Очікуваний результат |
| --- | --- | --- |
| AC-01 | Реєстрація, вхід, вихід, прострочений токен | Обліковий запис створюється, JWT дозволяє доступ, після виходу UI очищений, прострочений JWT відхиляється |
| AC-02 | Створення та редагування дошки | Автор стає адміністратором; зміни зберігаються після повторного відкриття |
| AC-03 | Додавання учасника та відкликання доступу | Дошка доступна доданому учаснику; після відкликання нові API-запити відхиляються |
| AC-04 | Обмеження створення та видалення карток | Заборони працюють і в UI, і в прямих API-запитах, включно з видаленням непорожньої колонки |
| AC-05 | Створення, перейменування, перестановка та видалення колонок | Порядок і назви зберігаються; видалення відповідає погодженому правилу |
| AC-06 | Створення та редагування всіх полів картки | Значення правильно відображаються й зберігаються; сторонній користувач не може бути відповідальним |
| AC-07 | Переміщення між колонками та всередині колонки | Картка має одну колонку, порядок зберігається після перезапуску клієнта |
| AC-08 | Коментарі двох користувачів | Відображаються текст, правильний автор та дата |
| AC-09 | Окремі й комбіновані фільтри та пошук | Результати відповідають умовам; скидання повертає повну дошку |
| AC-10 | JPG, PNG, WEBP, файл понад 5 МБ та хибний формат | Коректні фото мають превью й повний перегляд; недопустимі файли відхиляються |
| AC-11 | Перезапуск API та SQL Server | Користувачі, дошки, картки, порядок і фото збережені |
| AC-12 | Паралельне редагування та переміщення тієї самої картки | Конфлікт повідомляється; зміни не губляться непомітно, порядок залишається узгодженим |
| AC-13 | Робота 20 користувачів | Немає порушення цілісності; стандартні запити вкладаються у погоджений тест вимоги 2 секунд |
| AC-14 | Недоступний API під час drag-and-drop | UI реагує, показує помилку й відновлює збережений порядок |

Результати приймання мають містити фактичні запуски, сценарії та вимірювання. Наявність цього документа або успішна компіляція сама по собі не підтверджує виконання функціональних вимог.


Додаткове приймання PH-08 охоплює `FR-SKETCH-01`–`FR-SKETCH-07` та `FR-PROFILE-01`–`FR-PROFILE-04`: ролі/власник, ізоляція аватарів і обкладинок, коментарі, архів, зміна пароля/відкликання старих JWT, конфлікти та чернетки. Поелементна перевірка — [PH08_SCOPE](PH08_SCOPE.md), фактичні докази — [PH08_DESKTOP](PH08_DESKTOP.md).

## 7. Доповнення від 17.10.2026 — видалення аккаунта та іконка

Прямий запит користувача: власна іконка застосунку; можливість видалення власного аккаунта, але збереження аккаунта й дощок у БД протягом **7 днів**. Звичайний вхід правильним паролем до завершення строку скасовує заплановане видалення й повертає доступ до тих самих даних. Після строку відновлення вже недоступне; сервер виконує остаточну очистку.

Окремо користувач заборонив видаляти `demo.anastasiia@kanban.local`, `demo.olena@kanban.local`, `demo.dmytro@kanban.local`, `demo.iryna@kanban.local`. Вони мають постійний прапорець захисту в БД, який зберігається й після зміни email; API і фонове очищення перевіряють захист.

Погоджено користувачем: після 7 днів спільні дошки передаються іншому учаснику й зберігаються. Дошки без інших учасників видаляються. Історія збережених дощок анонімізується, призначення на видаленого користувача очищаються. До спливу строку ці зміни не виконуються. [Реалізація й докази](PH08_ACCOUNT_ICON.md).

## 8. Доповнення від 17.10.2026 — привітання й запам’ятовування входу

`FR-AUTH-REMEMBER-01`: за референсом користувача — привітальний екран із логотипом, описом можливостей, формами входу/реєстрації та тумблером «Запам’ятати мене». Увімкнений тумблер зберігає останній успішний сеанс локально для автоматичного входу після запуску. Вимкнення та «Вийти» прибирають збереження; можна увійти іншим аккаунтом. Пароль не зберігається. На macOS токен/email зберігаються у В’язці ключів, прив’язані до API. Сервер перевіряє токен перед відкриттям дощок; чинний строк JWT 24 години не подовжується. [Поведінка і докази](PH08_WELCOME.md).

## 9. Доповнення від 17.10.2026 — особистий чат

`FR-CHAT-01`: кнопка «Чат» біля іншого учасника «Команда» та розділ «Чати». `FR-CHAT-02`: особисті текстові повідомлення до 2000 символів, історія, дата/час, непрочитані, автоматичне оновлення. `FR-CHAT-03`: API-доступ лише для двох учасників, нова розмова через спільну дошку; наявна історія не залежить від подальшого членства. `FR-CHAT-04`: збереження MSSQL, повтор без дублікатів, чернетки та очищення пам’яті при виході. Додаткові дві таблиці розширюють початкову схему до 11; модель та п’ять міграцій задокументовані в [реалізації](PH08_PRIVATE_CHAT.md).
