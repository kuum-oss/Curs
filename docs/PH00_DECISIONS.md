# PH-00 — Рішення та уточнення KanbanBoard

Дата: 11.10.2026. Статус: PH-00 виконано; робочі рішення зафіксовано, MSSQL перевірено через емуляцію.

Основа: [фаза PH-00](PHASES.md#3-ph-00--уточнення-вимог-і-середовища), [вимоги](REQUIREMENTS.md) та [план реалізації](IMPLEMENTATION.md). Цей документ фіксує робочі правила перед PH-01; він не означає реалізацію функцій застосунку.

## 1. Рішення користувача

Користувач 11.10.2026 обрав три варіанти:

| ID | Рішення | Наслідок для реалізації |
| --- | --- | --- |
| D-01 | Перевірити MSSQL 2022 на поточному Mac через емуляцію | Використовувати образ SQL Server для `linux/amd64`; працездатність має підтверджуватися SQL-запитами, а не лише станом контейнера |
| D-02 | Базова версія працює на одному комп'ютері; 20 користувачів моделюються у тесті | API і SQL публікують порти лише на `127.0.0.1`; доступ із LAN не входить до базового запуску |
| D-03 | API і БД запускаються через Compose; Avalonia — нативно | Вимога запуску однією командою стосується серверної частини. Клієнт запускається окремо з Rider або як десктопний застосунок |

Емуляція не є офіційно підтримуваною Microsoft конфігурацією SQL Server. Навіть успішна проба підтверджує лише перевірений образ та середовище, а не будь-яку версію Docker чи образу. [Документація Microsoft](https://learn.microsoft.com/en-us/sql/linux/containers/deploy?view=sql-server-ver16).

Якщо сервер не працюватиме стабільно, PH-01 у частині MSSQL не можна вважати завершеною. Тоді потрібне окреме рішення про локальний x86-64 хост або налаштування емуляції; інша СУБД автоматично не підставляється.

## 3. Робочі правила предметної області

| ID | Робоче рішення | Документ-джерело |
| --- | --- | --- |
| D-04 | Один адміністратор на дошку — її автор. Передача ролі не реалізується; видалення власного адміністративного членства заборонене | [Ролі та права](REQUIREMENTS.md#2-ролі-та-права) |
| D-05 | Редагування й видалення дошки, надання/відкликання доступу та зміна дозволів — адміністратор. Учасники можуть працювати з колонками, редагувати й переміщувати картки та коментувати | [Матриця доступу](REQUIREMENTS.md#робоча-матриця-доступу) |

| D-13 | Теги належать дошці, їх назви унікальні без урахування регістру в межах дошки. Редагування/видалення коментарів і окреме керування життєвим циклом тегів не входять у базовий обсяг | [Картки](REQUIREMENTS.md#34-картки), [API](IMPLEMENTATION.md#4-контракт-api) |

## 5. План перевірки продуктивності

Це специфікація майбутнього тесту PH-08, а не отримані результати.

- 20 різних зареєстрованих користувачів із незалежними сесіями.
- 10 дощок, 10 колонок на дошку, 500 карток на дошку: разом 5 000 карток; частина дощок спільна для кількох користувачів.
- 2 хвилини прогріву; після них 15 хвилин вимірювань: 5 хвилин читання/пошуку, 5 хвилин змішаних стандартних операцій, 5 хвилин спільної роботи та конфліктів.
- Вимірюються список дощок, метадані відкритої дошки, колонки, картки, деталі, фільтрація, створення, редагування, видалення, коментарі та переміщення.
- Для кожного типу запитів фіксуються кількість, максимальний час, p95, неочікувані помилки й очікувані конфлікти окремо. Погоджена вимога стандартних операцій — не довше 2 секунд, а не лише p95 до 2 секунд.
- Конфліктні сценарії відокремлюються від звичайних записів: очікуваний `409` має відповідати збереженню цілісності, а не зараховуватися як випадковий збій.
- Після тесту перевіряються кількість та цілісність записів, членство, відповідальні й безперервний порядок позицій. Завантаження/читання фото та холодний запуск вимірюються окремо.
- Два реальних Avalonia-клієнти потрібні для наскрізної перевірки. Решту навантаження створює тестовий клієнт; двадцять відкритих GUI-вікон не потрібні.
- Машина, версії, ресурси Docker та перевірений digest SQL записуються у результати PH-08. Плавність drag-and-drop перевіряється в GUI; робоча ціль відгуку — до 100 мс.
