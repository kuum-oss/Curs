# PH-04 — Колонки, картки, теги та коментарі

Статус: виконано 12.10.2026 у гілці `ph-04`. Основа: [фаза PH-04](PHASES.md#7-ph-04--колонки-картки-теги-та-коментарі), [вимоги](REQUIREMENTS.md), [правила PH-00](PH00_DECISIONS.md), [контракт API](IMPLEMENTATION.md#4-контракт-api).

## Реалізований результат

Після відкриття дошки кнопка «Відкрити колонки та картки» завантажує її вміст. Колонки відображаються поруч із горизонтальною прокруткою; у кожній видно назви карток, пріоритет, дедлайн, відповідального та теги. Доступні створення, перейменування й видалення колонок, створення/редагування/видалення карток та редактор усіх полів, крім фото. Обкладинки належать PH-06.

Нові колонки й картки додаються в кінець. Після видалення позиції стають безперервними `0..N-1`. Переміщення й перестановка через drag-and-drop належать PH-05.

У редакторі є назва, опис, дедлайн `РРРР-ММ-ДД`, пріоритет Low/Medium/High/Critical, відповідальний із членів дошки або «Без відповідального», вибір тегів та створення нового тегу з кольором `#RRGGBB`. Типовий пріоритет — Medium. Теги унікальні за нормалізованою назвою в межах дошки; зв’язки картки з тегами замінюються атомарно. На картці можна вибрати до 100 тегів. Валідація полів має українські повідомлення.

Коментарі містять текст, справжнього автора та часову мітку UTC; клієнт показує локальну дату й час. Автор визначається JWT на сервері. Коментарі двох користувачів та збереження історії після відкликання членства перевірені. Редагування/видалення коментарів і окреме видалення тегів не входять у базовий обсяг.

## API

Префікс `/api`, усі маршрути захищені JWT.

| Метод | Маршрут | Дія |
| --- | --- | --- |
| GET / POST | `/boards/{boardId}/columns` | Колонки / створення |
| PUT / DELETE | `/boards/{boardId}/columns/{columnId}` | Перейменування / видалення |
| GET / POST | `/boards/{boardId}/cards` | Сторінка карток / створення з `ColumnId` у JSON |
| GET / PUT / DELETE | `/cards/{cardId}` | Деталі / редагування / видалення |
| GET / POST | `/boards/{boardId}/tags` | Теги дошки / створення |
| GET / POST | `/cards/{cardId}/comments` | Сторінка коментарів / додавання |

Створення повертає 201, читання й редагування — 200, видалення — 204. Усі мутації потребують `ExpectedBoardVersion`; зміни існуючої картки/колонки та додавання коментаря також потребують `ExpectedVersion` ресурсу. Для DELETE обидві версії передаються як URL-encoded Base64 у query `expectedBoardVersion` та `expectedVersion`. Для решти мутацій вони передаються в JSON.

Списки карток і коментарів приймають `offset >= 0`, `limit = 1..500`, типовий розмір — 100. Сторінка карток містить версію дошки й загальну кількість. На сервері її читання виконується у транзакції RepeatableRead через стратегію повторення EF; клієнт завантажує всі сторінки, приймає лише однакову версію та перевіряє її повторним читанням метаданих. За зміни дошки під час завантаження неповний стан не публікується. Пошук і фільтри належать PH-06.

## Права та цілісність

- Учасники можуть працювати з колонками, редагувати картки й коментувати. `CanCreateCards` і `CanDeleteCards` перевіряються незалежно для кожної мутації; адміністратор має повні права.
- Заборона видалення карток також забороняє видалити непорожню колонку. Порожню колонку видалити можна. UI приховує недоступні дії, прямий API повертає 403.
- Сторонній користувач отримує 404 для ресурсів чужої дошки. Відсутній JWT дає 401. Некоректні поля, чужий відповідальний або теги дають 400; конфлікт версії чи повторний тег — 409.
- `ColumnId`, відповідальний і всі теги перевіряються в межах тієї самої дошки. Повторення ID тегів відхиляється. Після відкликання членства старий JWT не відновлює доступ.
- Усі записи використовують `BoardAccess` PH-03: блокування дошки, повторна перевірка членства, перевірка версій і предметна зміна в одній транзакції. Це узгоджує призначення відповідального з відкликанням доступу.
- Видалення прибирає коментарі, зв’язки тегів і фото картки перед самою карткою. При видаленні колонки теги дошки залишаються. Штучна помилка наприкінці видалення колонки підтвердила повний відкат дочірніх записів та версії дошки.
- Додавання коментаря оновлює версію картки й дошки. Існуючі версії схеми PH-01 використано без нової міграції.

Конфлікт не повторює запис автоматично: клієнт показує помилку, отримує нові версії й зберігає чернетку. Наступне збереження — окрема дія користувача. За втрати доступу або виходу очищаються вміст, редактор, теги й коментарі; запізніла відповідь не відновлює кеш. Автоматичне періодичне оновлення належить PH-05.

## Відтворення та публікація

За готового SQL і локального `.env`:

```sh
scripts/dotnet.sh build Curs.sln -c Release
python3 scripts/verify-ph01.py ph04
scripts/dotnet.sh ef migrations has-pending-model-changes --project KanbanApi --no-build
python3 scripts/verify-ph04-http.py
```

HTTP-скрипт потребує Debug-збірки API; для GUI використати `--gui`, адресу клієнта `KANBAN_API_URL=http://127.0.0.1:5044/`, а після перевірки закрити клієнт і перервати скрипт для очищення БД. Повсякденний запуск — у [README](../README.md).

За вимогою користувача робота виконана в окремій гілці `ph-04`, без префікса `codex`. Порядок публікації: після успіху перевірок — push `ph-04`, перевірка її remote HEAD; потім fast-forward у `main`, push і перевірка remote HEAD `main`. Наступна фаза — PH-05.
