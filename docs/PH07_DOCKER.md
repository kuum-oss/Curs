## Реалізовано

Серверна частина запускається `docker compose up --build -d`; `--wait --wait-timeout 240` додатково очікує готовності обох сервісів. Avalonia лишається нативним клієнтом. SQL доступний на loopback 3038, API — 5000, внутрішні порти — 1433 та 8080. Параметри портів і назви БД необов’язкові; LAN не додавався.

Dockerfile має контекст кореня рішення, щоб включити KanbanContracts. SDK 10.0.103 і ASP.NET runtime 10.0.13 зафіксовані digest; digest MSSQL 2022 з PH-00 збережено. API публікується для Linux-архітектури хоста і працює як непривілейований користувач. Готовий образ не містить SDK, клієнта, тестів або локального .env; allowlist .dockerignore відсікає сторонні файли та bin/obj.

Compose очікує SQL healthcheck SELECT 1. Перед відкриттям HTTP API перевіряє JWT-конфігурацію й застосовує міграції. Помилка конфігурації або міграції дає керований вихід 1, без відкриття порту. Liveness перевіряє процес, readiness — SQL і відсутність незастосованих міграцій. Healthcheck образу звертається до readiness через той самий dotnet binary в режимі --healthcheck, без SDK/curl і другого сервера. Restart unless-stopped налаштовано для обох сервісів; unhealthy сам по собі не означає restart.

При ліміті Docker 7,8 ГіБ перша публікація всіх платформ Magick.NET не вмістилася. Публікацію обмежено linux-$TARGETARCH; файли API у фінальному шарі скоротилися приблизно з 418 до 76 МБ. Restore, publish та видалення кешу пакетів виконуються в одному шарі. Видалено лише точно визначені записи власної невдалої/проміжної збірки; робочий SQL volume не видалявся. Ліміт Docker не змінювався. Кеш проміжного шару остаточної публікації — близько 246 МБ; мережевий NuGet HTTP-кеш може лишатися в build stage, але не в runtime.

У негативній перевірці старої збірки необроблений виняток старту лишав одноразовий контейнер працюючим; його завершено вручну. Цей діагностичний прогін не використано як доказ правильного коду виходу. Після додавання керованого завершення весь сценарій повторено на остаточному образі: обидва негативні запуски самостійно повернули саме 1. Перший діагностичний протокол лишився тільки у виключеному з Git TestResults.

Автоматичний сценарій запущено зі свіжими випадковими секретами, вільними loopback-портами та власною новою БД. Порівнюються повні JSON-знімки до/після й хеші бінарних відповідей, а не лише кількість записів. Паролі й JWT не входять до фазового протоколу. Живий GUI підключено до того самого остаточного образу після автоматичних перезапусків; початкова read-only GUI-перевірка теж пройшла, але опубліковані знімки оновлено на фінальному стенді.

Виконано NFR-05, NFR-06 та AC-11 у перевіреному локальному середовищі. Це не робить MSSQL на ARM офіційно підтримуваною платформою. Навантаження 20 користувачів і загальну вимогу двох секунд буде перевірено у PH-08.

## Відтворення

```sh
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 240
scripts/dotnet.sh build Curs.sln -c Release
python3 scripts/verify-ph01.py ph07
python3 scripts/verify-ph07-docker.py
KANBAN_API_URL=http://127.0.0.1:5000/ scripts/dotnet.sh run --project Curs
```

Підготовка секретів, штатна зупинка й persistent volume описані у [DEPLOYMENT](DEPLOYMENT.md). Скрипт не використовує down -v робочого проєкту; прибирає лише власний випадково названий том. При зміні коду повторна збірка може відновлювати пакети з мережі.

Офіційні джерела: [контейнери .NET](https://learn.microsoft.com/en-us/dotnet/core/docker/build-container), [порядок старту Compose](https://docs.docker.com/compose/how-tos/startup-order/), [health checks ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/health-checks?view=aspnetcore-10.0). Фактичні digest зафіксовані у Dockerfile/Compose та перевірені реєстром MCR під час фази.

Наступна фаза — PH-08: приймання, навантаження й матеріали захисту. Публікація: push ph-07 та перевірка remote HEAD, потім fast-forward main, push і перевірка remote HEAD.
