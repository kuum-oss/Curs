# PH-08 — інтерфейс за ескізами та власний профіль

Стан на 16.10.2026: фаза у роботі. Реалізація й наведені нижче перевірки не замінюють завершення всієї [матриці приймання](PH08_SCOPE.md).

## Реалізована структура

Замість вертикального набору форм клієнт має спільну ліву панель, сітку дощок у три стовпці, чотири видимі Kanban-колонки при цільовому розмірі вікна та окремий шар модальних редакторів. Колонки прокручуються незалежно; редактор має фіксовані верхню й нижню панелі та прокручуваний вміст для невеликого вікна.

Дані плиток, лічильники, аватари, описи та обкладинки надходять із API. «Обране» і «Останні» персональні для учасника. «Особисті задачі» показують призначені поточному користувачеві картки всіх його дощок; «Команда» — співучасників; «Архів» дозволяє відновлювати дошки й картки.

Картка показує обкладинку, опис, кольоровий пріоритет, кольорові теги, дедлайн, кількість коментарів та аватар відповідального. Редактор містить календар, вибір відповідального з аватаром, теги з додаванням/прибиранням, фото, повний перегляд та коментарі з меню дій. Після першого збереження нової картки можна завантажити фото й додати коментарі.

Окрема сторінка профілю змінює ім’я, email, аватар і пароль. Зміна email вимагає поточного пароля; новий пароль — поточного пароля й підтвердження. У разі зміни пароля сервер видає новий JWT, а попередні JWT цього користувача більше не приймає. Паролі лишаються BCrypt-хешами; термін JWT — 24 години.

## API розширення

| Метод і маршрут | Дія та захист |
| --- | --- |
| `PUT /api/profile` | Власні ім’я/email; `ExpectedVersion`, поточний пароль для зміни email |
| `PUT /api/profile/password` | Власний пароль; версія профілю, поточний пароль, новий пароль і підтвердження |
| `PUT /api/profile/avatar` | Multipart: `File`, `ExpectedVersion` |
| `DELETE /api/profile/avatar` | Версія профілю в query |
| `GET /api/users/{id}/avatar` | Лише власник або поточний співучасник; PNG, private/no-store |
| `PUT /api/boards/{id}/cover` | Адміністратор; multipart `File`, `ExpectedBoardVersion` |
| `GET /api/boards/{id}/cover` та `/thumbnail` | Лише поточний учасник; private/no-store |
| `DELETE /api/boards/{id}/cover` | Адміністратор і актуальна версія дошки |
| `PUT /api/boards/{id}/members` | Атомарне збереження ролей/дозволів; актуальна версія дошки |
| `PUT /api/boards/{id}/favorite` | Лише власна позначка поточного учасника |
| `POST /api/boards/{id}/visit` | Лише власна дата останнього відкриття |
| `PUT /api/boards/{id}/archive` | Архівування/відновлення дошки адміністратором із перевіркою версії |
| `PUT /api/cards/{id}/archive` | Архівування/відновлення картки за правом видалення й версіями дошки/картки |
| `PUT /api/cards/{id}/comments/{commentId}` | Редагування власного коментаря; версії дошки, картки й коментаря |
| `DELETE /api/cards/{id}/comments/{commentId}` | Власний коментар або адміністратор; ті самі три версії |
| `GET /api/me/cards` | Пагінація, `archived`, `assignedOnly`; лише доступні поточному користувачеві дошки |
| `GET /api/me/team` | Лише користувачі зі спільних поточних дощок |

Стандартний список карток приховує архівовані картки. `archived=true` запитує архів. Переміщення архівованої картки відхиляється до її відновлення. Невалідні файли й фото понад 5 МіБ не замінюють попередню обкладинку; JPG, PNG і WEBP проходять фактичне декодування.

## Дані, конкуренція та сесія

Залишаються дев’ять таблиць початкового ТЗ. Друга EF-міграція додає поля профілю/сеансу, обкладинку й архів дошки, персональне обране/дату відкриття, архів картки та версію/дату редагування коментаря. Міграція визначає початкового власника з наявного адміністратора, не очищає дані й дозволяє додаткових адміністраторів. Власника не можна позбавити адміністрування або вилучити.

Зміни профілю, видимі співучасникам, змінюють версії відповідних дощок. Сервер перевіряє членство до та після читання приватних фото. Клієнт оновлює дані кожні п’ять секунд; чернетки зберігаються при конфлікті, а втрата доступу очищає також відкритий приватний редактор. Незбережені зміни мають підтвердження перед закриттям/переходом; скасований запит зміни пароля не може повторно авторизувати користувача після виходу.

## Перевірені результати

- Release: 0 помилок і 0 попереджень.
- 104 тести, 0 пропусків, включно з реальною MSSQL, переходом із початкової міграції, відкликанням JWT, ізоляцією фото, власником/ролями, архівом, коментарями та очищенням приватного чернеткового редактора після відкликання доступу.
- [Навантажувальний протокол](PH08_LOAD_RESULTS.json): 20 реальних авторизованих користувачів, 442 стандартні запити; максимум 488,227 мс, p95 340,738 мс. Одна конкурентна зміна картки прийнята, 19 відхилено з 409. Перезапуск production API зберіг результати всіх 20 сценаріїв.
- У живому Avalonia підтверджено створення дошки/колонки та збереження всіх полів картки, тегу, фото через macOS file picker, коментаря й дозволів учасника; значення повторно прочитані API. Решта перевірок GUI продовжуються за матрицею.

Навантаження використовує окрему тимчасову БД у наявному MSSQL-контейнері та додатковий контейнер того самого production API-образу. Створення акаунтів і послідовний вхід вимірюються окремо; робочі сценарії запускають 20 сесій одночасно. Це вимірювання локального стенда, без обіцянки для довільного апаратного середовища. Тимчасову БД і контейнер прибрано; робочий volume збережено.

Повторний запуск: `python3 scripts/verify-ph08-load.py` після готовності Compose. Потрібні наявний `.env` та зібраний образ `kanbanboard-api:local`. Протоколи без секретів записуються в `TestResults`; середовище з паролями лишається виключеним із Git.
