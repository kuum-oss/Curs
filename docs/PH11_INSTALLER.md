# PH-11 — Встановлення та готові desktop-релізи

Виконано: 03.11.2026. Гілка: `release-installer`. Опублікований реліз: [0.2.0](https://github.com/kuum-oss/Curs/releases/tag/v0.2.0).

Мета фази — встановлення на Windows і macOS без SDK, вихідного коду та ручного виконання команд. Реліз містить наявний Avalonia-клієнт із власним .NET runtime, а API постачається готовим Docker-образом. Інструкція встановлення, склад файлів та порядок випуску: [RELEASES.md](RELEASES.md).

## Пакети

| Платформа | Пакет | Поведінка |
| --- | --- | --- |
| Windows x64 | Inno Setup `.exe` та ZIP | Установлення для поточного користувача, ярлик у меню програм, необов’язковий ярлик на робочому столі, пропозиція відкрити KanbanBoard |
| macOS 15+, Apple Silicon | DMG та ZIP із `.app` | Копіювання програми до Applications; власний ARM64 .NET runtime |
| macOS 15+, Intel | DMG та ZIP із `.app` | Копіювання програми до Applications; власний x64 .NET runtime |

Видалення клієнта прибирає програмні файли й ярлики; дані застосунку та Docker volume не входять до правил видалення установника. Пакувальник відхиляє непорожню вихідну папку й не перезаписує довільні попередні збірки.

## Перший та повторний запуск

Майстер показує три етапи: перевірку Docker Desktop, отримання серверних компонентів і перевірку готовності. До першої підготовки потрібно окремо прийняти умови SQL Server Developer. Згода зберігається для конкретного SQL-образу; майстер не приймає ліцензійні умови Docker замість користувача.

За відсутності Docker доступна кнопка завантаження офіційного установника. Встановлення, системні дозволи й можливе перезавантаження Windows відбуваються у його штатних вікнах. Якщо Docker установлено, але він не працює, майстер пропонує запуск та повторну перевірку. Під час підготовки видно поточний етап і прогрес; операцію можна скасувати та повторити.

Серверний архів завантажується з URL конкретної версії GitHub Release. SHA-256 із вбудованого `setup/runtime.json` перевіряється **до** додавання образу до Docker. Після завантаження перевіряються архітектура й ID образу. Пошкоджений архів не запускається. Збережений перевірений архів та вже підготовлений образ використовуються повторно.

Після запуску контейнерів перевіряються їхній власник, образи, мережеві налаштування та `/health/ready`. Основне вікно відкривається лише після готовності сервера і БД. Повторний запуск використовує ті самі облікові дані компонентів, порт та volume. Неповні або неузгоджені налаштування не перезаписуються автоматично.

За наявності явно заданого `KANBAN_API_URL` клієнт підключається до вказаного сервера. У dev-збірці без релізного manifest зберігається звичайний спосіб запуску.

## Ізоляція та збереження даних

Кожне встановлення отримує випадковий ID і окремий Compose-проєкт `kanbanboard-desktop-<id>`. Контейнери та volume мають мітку цього встановлення. Перед змінами майстер перевіряє її та зупиняється, якщо знаходить чужі компоненти. Він не використовує назву штатного dev-стенду й не виконує видалення або скидання БД.

API доступний лише через випадково вибраний порт `127.0.0.1`; SQL не публікує порт на хості. Пароль SQL та ключ JWT генеруються локально й зберігаються поза програмним пакетом. На Unix папка компонентів має права `0700`, файли з обліковими даними — `0600`. Одночасна підготовка захищена файловим блокуванням. Повідомлення майстра не виводять секрети чи необроблений журнал Docker.

MSSQL має зафіксований digest Linux x86-64 образу. На Apple Silicon він потребує емуляції Docker; ARM64 API використовує нативний образ. SQL Server Developer призначений для розробки, тестування й демонстрацій.

Локальні результати записані в ігнорованій папці `TestResults`: `setup-release-candidate.trx`, `setup-release-candidate.log`, `release-packaging-tests.log`, `runtime-smoke-build.log`. [Опис нативного знімка](screenshots/installer/README.md) відокремлює перевірений вигляд від ще не завершеної підготовки сервера.

`RuntimeSmoke` має захист від локального запуску: потрібні Linux, `GITHUB_ACTIONS=true`, `RUNNER_TEMP` і шляхи двох серверних artifacts. Він перевіряє розпакування готового образу, окремий Compose-проєкт, міграції, реєстрацію синтетичного користувача, створення дошки та її збереження після зупинки й повторного запуску власного стенду. Очищення стосується лише його тимчасового проєкту.

**У межах PH-11 локальну Docker-БД не змінено.** Локальні перевірки не запускали Compose, міграції чи SQL-тести. Перевірки зі справжнім MSSQL виконуються на окремих тимчасових сервісах GitHub Actions; вони не підключаються до локального dev-стенду.
