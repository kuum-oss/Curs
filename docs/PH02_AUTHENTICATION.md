## 1. Реалізовані сценарії

| Запит | Результат |
| --- | --- |
| `POST /api/auth/register` | Приймає email, ім'я та пароль; створює користувача й повертає 201 з токеном, строком дії та UserDto |
| `POST /api/auth/login` | Перевіряє BCrypt-хеш і повертає 200 з даними сесії |
| `GET /api/auth/me` | Захищений JWT; повертає актуальні дані користувача з MSSQL |
| Вихід у клієнті | Прибирає токен, користувача, поля форм і стан навігації; відкриває вхід |

Email нормалізується без урахування регістру; ім'я й email обрізаються по краях. Пароль не нормалізується й не обрізається. Валідація відхиляє некоректний email, порожнє ім'я, перевищення лімітів та пароль коротший за 8 UTF-16 одиниць, довший за 72 байти UTF-8 або з нульовим символом. Пароль рівно на 72 байти перевірено окремим тестом.

Повторний email повертає `409 email_exists`, включно з паралельною реєстрацією. Унікальний SQL-індекс залишається остаточним захистом. Неправильний пароль і невідомий користувач дають однакові `401 invalid_credentials`. Для відсутнього облікового запису також виконується BCrypt-перевірка фіктивного хешу.

Використано BCrypt.Net-Next 4.2.0 з work factor 12 і окремою випадковою сіллю для кожного хешу. JWT підписується HS256 та містить `sub`, `jti`, `iat`, `nbf`, `exp`, issuer і audience. Різниця `exp - nbf` — рівно 24 години; строк у відповіді відповідає `exp`. Права дошок не записуються в токен.

API перевіряє підпис, алгоритм, issuer, audience, строк дії та коректний Guid у `sub`; `ClockSkew = 0`. Відсутній, підроблений, непідписаний, прострочений або передчасний токен дає 401 з ProblemDetails та Bearer challenge. Видалений користувач не може прочитати `/me` зі старим JWT. Параметри валідації відповідають [документації Microsoft](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0); пакет BCrypt — [реєстр NuGet](https://www.nuget.org/packages/BCrypt.Net-Next/4.2.0).

## 2. Клієнт Avalonia

Головне вікно має форми входу й реєстрації, масковане поле пароля, відображення помилок та блокування повторного відправлення під час запиту. Після успіху клієнт зберігає сесію в пам'яті й переходить до початкового екрана «Мої дошки». Список і керування дошками реалізуються у PH-03.

Bearer додається до кожного запиту; 401 чинної сесії повертає клієнт до входу. Запізнілий 401 старої сесії не очищає нову. Невдалий анонімний вхід зберігає email для повторної спроби; пароль очищається після завершення запиту. Вихід скасовує активний запит, тому пізня відповідь входу не відновлює сесію.

При виході й закритті застосунку прибираються посилання на дані сесії; токен не записується на диск. Предметного кешу дощок/фото у цій фазі ще немає. Серверного відкликання JWT при виході не передбачено вимогами: виданий токен діє до завершення строку.

## 3. Запуск і конфігурація

Локальний `.env` має містити власні `MSSQL_SA_PASSWORD` та випадковий `JWT_KEY` щонайменше на 32 байти. Відсутній, короткий або шаблонний секрет з `.env.example` зупиняє запуск API. Секрети не включаються у Git.

У Development значення можуть читатися з локального `.env`. Поза Development передати `ConnectionStrings__Default` та `JWT_KEY` або `Jwt__Key` через конфігурацію середовища. За потреби `Jwt__Issuer` та `Jwt__Audience` змінюють типові `KanbanBoard.Api` й `KanbanBoard.Desktop`.

```sh
docker compose up -d sqlserver
scripts/dotnet.sh run --project KanbanApi
```

У другому терміналі:

```sh
scripts/dotnet.sh run --project Curs
```

Типовий URL клієнта — `http://localhost:5000/`. Він змінюється через `KANBAN_API_URL`. API працює нативно, SQL — у Docker; Dockerfile сервера залишається роботою PH-07.

## 4. Перевірки

```sh
scripts/dotnet.sh build Curs.sln -c Release
python3 scripts/verify-ph01.py ph02
python3 scripts/verify-ph02-http.py
```

| Перевірка | Фактичний результат |
| --- | --- |
| Release | 0 помилок, 0 попереджень |
| Автоматизовані тести | 31 пройшов, 0 помилок, 0 пропусків; 16 сценаріїв використовують реальний MSSQL |
| Регресія PH-01 | Усі попередні 19 тестів пройшли |
| Нові серверні перевірки | 6 SQL-сценаріїв auth плюс перевірка конфігурації секрету |
| Нові клієнтські перевірки | 5 сценаріїв: вхід/вихід, помилки, скасування входу, реєстрація/401, збереження email |
| Нативний API через HTTP | 8 запитів з очікуваними 201/200/409/401 |
| Avalonia на macOS | Реєстрація, невірний пароль, повторний вхід, `/me`, вихід та повторний запуск перевірені у живому вікні |
| Аудит NuGet | Відомих вразливих пакетів, включно з транзитивними, не повідомлено на дату перевірки |
| EF-модель | Змін, що потребують нової міграції, немає |

SQL-тести та HTTP/GUI-перевірка використовували окремі тимчасові БД; їх прибрано після виконання. HTTP-скрипт сам запускає API на loopback-порту 5042 (порт має бути вільним) та зупиняє його після перевірки. `--gui` залишає API для ручної перевірки клієнта до переривання, після якого тестову БД також прибирає. Перед HTTP-перевіркою зібрати Debug API, якщо його ще немає: `scripts/dotnet.sh build KanbanApi`.

Для доступу до непакованого Avalonia-процесу засобами перевірки GUI створено локальний тестовий `.app` у `TestResults`; він не є інсталяційним пакетом і не публікується. У Git збережено лише скриншоти та протокол без паролів/токенів. Сирі TRX, журнал API й локальні результати залишаються в ігнорованому `TestResults`.

Окремі HTTP-вимірювання наведено у протоколі; вони не підтверджують навантаження 20 користувачів або виконання загального NFR часу відповіді. Приймання навантаження — PH-08. Наступна фаза — PH-03: дошки, учасники та права.
