# PH-08 — відновлення аккаунта протягом 7 днів, захист demo та іконка

Реалізовано за прямими вказівками користувача від 17.10.2026: власна іконка, видалення свого аккаунта, 7 днів для повернення, недоторканність чотирьох demo-аккаунтів та збереження спільних дощок після строку. [Вимоги](REQUIREMENTS.md#7-доповнення-від-17102026--видалення-аккаунта-та-іконка), [машинний протокол](PH08_ACCOUNT_ICON_RESULTS.json).

## Поведінка

Профіль → «Видалити мій аккаунт» → переглянути наслідки → ввести поточний email і пароль → «Запланувати видалення». До підтвердження можна скасувати дію. API фіксує строк **рівно 7 × 24 години** у UTC, відкликає старі JWT та залишає в БД аккаунт, аватар, членства, власність, колонки, картки, призначення, коментарі й фото.

Звичайний вхід правильним паролем **до** кінцевої дати атомарно скасовує видалення; зберігаються той самий ID і доступ до дощок. Новий сеанс має новий номер; старі JWT залишаються недійсними. Неправильний пароль не скасовує строк, а повторна реєстрація на зайнятий email не обходить відновлення. Починаючи з точної кінцевої дати вхід відхиляється.

Якщо користувач не повернувся, фоновий сервіс:

- передає спільні дошки іншому учаснику: спочатку активному, далі адміністратору, потім найранішому учаснику;
- видаляє власні дошки без інших учасників разом із їхнім вмістом;
- залишає спільні картки, фото та коментарі, очищує посилання на автора; коментарі показуються від імені «Видалений користувач»;
- прибирає членства й призначення та фізично видаляє рядок профілю з email, ім’ям, хешем пароля й аватаром.

Очищення запускається при старті API та щохвилини, пакетами до 20 аккаунтів, із повторною перевіркою строку під блокуванням. Якщо API вимкнений, прострочені записи обробляються після наступного запуску. Новий вхід після строку не дозволяється в очікуванні циклу очищення. Передача визначається за актуальними учасниками на момент очищення.

## Чотири захищені demo-аккаунти

`demo.anastasiia@kanban.local`, `demo.olena@kanban.local`, `demo.dmytro@kanban.local`, `demo.iryna@kanban.local` мають постійний `IsProtectedDemo`. Міграція встановлює його на наявних рядках; реєстрація на ці адреси також встановлює захист. Зміна email не скидає прапорець. API не дає навіть розпочати попередній перегляд видалення; фонове очищення повторно перевіряє прапорець і відомі адреси. У профілі кнопка вимкнена та показано пояснення.

У робочій БД підтверджено: **усі чотири початкові ID збережені, вхід працює, захист увімкнений**. Запитів `DELETE` до цих аккаунтів під час перевірки не надсилали. Автоматичні інтеграційні тести використовують випадкові аккаунти в окремих тимчасових БД; HTTP-перевірка робочого образу — два окремі випадкові тестові аккаунти.

## API, БД та клієнт

| Маршрут | Результат |
| --- | --- |
| `GET /api/profile/deletion-preview` | Наслідки для власних дощок, версія і токен стану; `private, no-store`; demo — 403 |
| `DELETE /api/profile` | Пароль, email, версія й токен перегляду; **202** із `deletionDueAtUtc`, без негайного видалення |
| `POST /api/auth/login` | Скасовує незавершене видалення до строку, повертає `accountRestored=true`; після строку — 401 |

Зміна стану дощок або майбутнього отримувача після попереднього перегляду вимагає нового підтвердження. Запит і остаточне очищення виконуються транзакційно, з блокуваннями дощок перед профілем. Вхід блокує рядок профілю й повторно перевіряє актуальний строк, тому не може воскресити запис одночасно з очищенням.

Залишаються дев’ять таблиць. Третя міграція робить авторські зовнішні ключі nullable; четверта додає два UTC-поля строку, його індекс, перевірку рівно семи днів та захист demo. Модель EF відповідає міграціям. Зворотні міграції не дозволяють втратити активний строк або вигадати автора анонімізованої історії.

Клієнт показує правило 7 днів у діалозі й на вході, дату після запиту та повідомлення після відновлення. Скасування й вихід очищають чутливі поля; запізніла відповідь старої сесії не виходить із нового аккаунта й не стирає його чернетку.

## Перевірки

**131 тест пройдено, 0 помилок і 0 пропусків** із реальною MSSQL. Release — 0 помилок і 0 попереджень. Перевірені сім днів без очікування календарного тижня: керований час у SQL-тестах, точна межа, відновлення, конкуренція зі входом, захист demo після зміни email, міграції, анонімізація, передача власності та ізоляція сесій.

**33 HTTP-запити** до production Docker API підтвердили запит → збереження → вхід/відновлення → повторний запит → фонове очищення → передачу спільної дошки → очищення останнього власника. Для прискорення виключно у двох власних випадкових тестових записів SQL переносив часові поля в минуле; видалення виконував справжній фоновий сервіс. SQL-запит додатково звірив відсутність обох тестових користувачів, дошки й картки. Оригінал PNG та превью працюють у Linux-образі; чотири demo збережені й захищені.

Перед оновленням авторських полів та після нього точний digest тестової наявної дошки збігся: 10 карток, 10 медіаресурсів, поля, коментарі, ролі й версії. Четверта міграція навмисно змінює версії чотирьох профілів при встановленні захисту; їхні ID і дані входу збережені.

Нативний діагностичний запуск підтвердив завантаження стилів/XAML, завершення ініціалізації та відкриття головного вікна. Візуальне приймання остаточного екрана не підтверджене: після розблокування Mac інструмент управління вікнами повторно повертав `timeoutReached`. Це обмеження записано окремо від успішних автоматичних перевірок; нових скриншотів не заявлено.

```sh
scripts/dotnet.sh build Curs.sln -c Release
KANBAN_TEST_CONFIGURATION=Release python3 scripts/verify-ph01.py account-recovery-acceptance
scripts/dotnet.sh ef migrations has-pending-model-changes --project KanbanApi --configuration Release --no-build
docker compose up -d --build --wait
python3 scripts/verify-account-deletion.py
scripts/package-macos.sh
```

HTTP-скрипт працює лише з `127.0.0.1:5000` і власними випадковими `delete-check-…@example.test`; зміщення часу додатково обмежене ID, префіксом email, наявним запитом видалення й відсутністю demo-захисту. Паролі/JWT не записуються до протоколу чи Git. Робочий SQL volume не видалявся.

## Виправлення після перевірки користувачем 17.10.2026

Користувач показав стандартну іконку macOS у Dock і недоречну постійну підказку про видалення на звичайному вході. `Window.Icon` та іконка пакета не покривали всі способи запуску. Додано встановлення вбудованого PNG через [NSApplication.applicationIconImage](https://developer.apple.com/documentation/appkit/nsapplication/applicationiconimage) після ініціалізації Avalonia. Це працює також при запуску через Rider / `dotnet`, незалежно від кешу іконки пакета. Інші платформи пропускають нативний виклик.

Постійну підказку про 7 днів прибрано з входу та реєстрації. Після фактичного запиту видалення залишається повідомлення: «Обліковий запис буде видалено [дата] о [час]. Щоб скасувати видалення, увійдіть протягом 7 днів». Правила збереження даних і захист demo не змінювалися.

Повторно перевірено: Release — 0 помилок / 0 попереджень; усі 4 `DesktopAccountDeletionTests` пройшли; `.app` оновлено. Нативний стенд запустив клієнт без пакета, прочитав власний `NSApplication.applicationIconImage`, експортував його TIFF та завершився з кодом 0. Експортоване зображення оглянуто: власний бірюзовий логотип замість стандартного значка. CUA після перезапуску показав звичайний екран входу без підказки, що підтверджено деревом доступності та скриншотом. Прямий знімок Dock інструмент не отримав (`timeoutReached`), тому окремий скриншот Dock не заявляється.

Локальні ігноровані докази: `TestResults/icon-login-build.log`, `icon-login-desktop.trx`, `icon-login-native-probe.log`, `icon-login-running-dock.png`. Виправлення: `0fe1223` — нативна іконка, `dbd7550` — текст входу.
