# PH-01 — Основа рішення та база даних

Дата: 11.10.2026. Статус: **Виконано**.

Фаза реалізує [PH-01 у плані фаз](PHASES.md#4-ph-01--основа-рішення-та-база-даних), спираючись на [архітектуру та модель даних](IMPLEMENTATION.md#1-архітектура), [вимоги](REQUIREMENTS.md) і [рішення PH-00](PH00_DECISIONS.md). Фактичні результати перевірок збережено у [PH01_RESULTS.json](PH01_RESULTS.json).

## 1. Що реалізовано

| Частина | Результат |
| --- | --- |
| Рішення | Чотири проєкти: `Curs`, `KanbanApi`, `KanbanContracts`, `KanbanApi.Tests`; .NET 10 |
| Контракти | DTO дошок, учасників, колонок, карток, тегів, коментарів; enum ролей/пріоритетів, ліміти полів та модель помилок без залежності від EF |
| SQL-модель | Дев'ять таблиць: Users, Boards, BoardMembers, Columns, Cards, Tags, CardTags, CardImages, Comments |
| Цілісність | PK/FK, складені ключі, унікальність email/тегів/обкладинки, один адміністратор максимум, індекси, CHECK-обмеження, `rowversion` |
| Міграція | `20261011201833_InitialCreate` застосована до `KanbanDB` у MSSQL 2022; повторне застосування не змінює схему |
| Основа API | DI, конфігурація SQL, обмежені повтори підключення, застосування міграцій перед стартом, health endpoints, ProblemDetails та помилки валідації |
| Основа клієнта | HttpClient, Bearer для кожного запиту, сесія в пам'яті, очищення після 401, навігація, повідомлення MVVM у головному вікні |

Усі зовнішні ключі мають `NO ACTION`: неявне каскадне видалення не прибирає дочірні дані. Сервіси майбутніх фаз повинні явно виконувати погоджені видалення в транзакції. Унікальний фільтрований індекс обмежує кількість адміністраторів; створення обов'язкового адміністратора і перевірку належності відповідального/тегів до дошки забезпечуватимуть предметні сервіси.

Оригінал і превью зображення зберігаються у `varbinary(max)`. Схема обмежує оригінал до 5 МБ та перевіряє відповідність `SizeBytes` реальній довжині. Декодування JPG/PNG/WEBP, завантаження й показ фото реалізуються у PH-06.

Невідомі серверні винятки повертають загальне повідомлення 500 без деталей винятку; передбачені помилки мають стабільні `code` і `traceId`, а валідація — помилки полів. Запізніла відповідь 401 зі старої сесії не очищає нову сесію. Клієнт підтримує скасування запитів і відхиляє абсолютні адреси в операціях API.

## 2. Середовище та запуск

Перевірено на поточному Mac ARM64: повний SDK 10.0.103, runtime 10.0.3, EF Core 10.0.12, Avalonia 11.3.12, SQL Server 2022 Developer 16.0.4295.3 через емуляцію `linux/amd64`.

Системний SDK мав неповну інсталяцію без потрібних reference packs. Для перевірки використано повний офіційний SDK тієї самої версії в ігнорованому `.tools/dotnet`. `global.json` фіксує версію; `scripts/dotnet.sh` вибирає цей локальний SDK за його наявності або системний. Вимкнення перевірок пакетів до проєктів не додано. SDK та його архів не публікуються в Git.

Підготувати `.env` за `.env.example` з власними значеннями; локальний `.env` не комітити. Інструкція запуску також наведена в [README](../README.md#підготовка-локального-середовища).

```sh
docker compose config --quiet
docker compose up -d sqlserver
scripts/dotnet.sh tool restore
scripts/dotnet.sh run --project KanbanApi
```

API у Development читає пароль з локального `.env`, підключається до `localhost,3038`, створює/оновлює `KanbanDB` міграціями перед прийманням запитів і слухає `http://localhost:5000`. Якщо міграція не виконується в межах часу запуску, API не переходить до приймання запитів. Для іншого середовища передати `ConnectionStrings__Default`. За потреби міграцію можна застосувати окремо:

```sh
scripts/dotnet.sh ef database update --project KanbanApi
```

Клієнт запускається в окремому терміналі:

```sh
scripts/dotnet.sh run --project Curs
```

Типова адреса API — `http://localhost:5000/`; змінна `KANBAN_API_URL` дозволяє задати іншу HTTP(S)-адресу. Для Rider вибрати повний .NET SDK; локальний шлях на перевіреній машині — `.tools/dotnet/dotnet` відносно кореня репозиторію.

## 3. Фактичні перевірки

```sh
scripts/dotnet.sh build Curs.sln -c Release
python3 scripts/verify-ph01.py
scripts/dotnet.sh ef migrations has-pending-model-changes --project KanbanApi
```

| Перевірка | Результат |
| --- | --- |
| Release-збірка всього рішення | Успіх; 0 попереджень, 0 помилок |
| Повний набір тестів | 19 пройшли, 0 помилок, 0 пропусків |
| Міграція в реальному `KanbanDB` | Дев'ять предметних таблиць плюс службова історія EF; повторне застосування — без змін |
| Відповідність моделі міграції | Незбережених змін моделі немає |
| HTTP `/health/live` | 200, `status: live` |
| HTTP `/health/ready` | 200, `status: ready` з реальною БД |
| HTTP невідомого маршруту | 404 з ProblemDetails та `code: not_found` |
| Тестовий контролер у звичайному API | Відсутній; тестова адреса повернула 404 |
| Робочі дані після тестів | `Users = 0`, `Boards = 0`; тестові записи не потрапили в робочу БД |

Вісім SQL-тестів перевіряють міграцію та її повторне застосування, повний граф даних з Unicode/датами/бінарними полями, унікальність email без урахування регістру, заборону другого адміністратора, CHECK-обмеження, FK та одну обкладинку, конфлікт `rowversion`, відсутність прихованого каскаду й відкат транзакції. Окремо перевірено модель, чотири сценарії основи API/readiness та шість клієнтських сценаріїв.

SQL-тести використовують окрему тимчасову БД з випадковим іменем і видаляють її після виконання. Скрипт передає підключення через середовище без друку пароля. Без `KANBAN_TEST_CONNECTION` SQL-тести пропускаються; наведений скрипт забезпечує повний запуск. Сирі TRX/HTTP-результати залишаються в ігнорованому `TestResults`; підсумок і назви тестів опубліковано в [JSON-протоколі](PH01_RESULTS.json).

## 4. Межі завершеної фази

Реєстрація, BCrypt, видача/перевірка JWT та екрани входу належать до PH-02. Наявність клієнтського Bearer-handler не означає готовність серверної автентифікації. CRUD дошок, карток, фото, drag-and-drop та предметна валідація залишаються у відповідних наступних фазах.

API перевірено нативним процесом, SQL — у Docker. Dockerfile і повний Compose-запуск API додаються у PH-07. Фактична робота Avalonia GUI, 20 користувачів та ліміт запитів 2 секунди у PH-01 не перевірялися. Поточні автоматизовані перевірки підтверджують основу й схему, а не завершені користувацькі сценарії.

Наступна фаза — [PH-02: автентифікація та сесія](PHASES.md#5-ph-02--автентифікація-та-сесія). Блокуючих питань для її початку немає.
